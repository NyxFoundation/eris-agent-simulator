# 採点メトリクスの実測記録

**この文書は何か**: DeFi トレード競技の順位をどの数式で決めるかを選ぶための測定記録です。候補が複数あり
どれも「もっともらしい」ため、**同じ run を全候補で採点し直して、どこで結論が食い違うか**を見ています。
設計の決定そのものは `docs/adr/0019-competition-scoring-metric-continuous-economy.md`（以下 ADR 0019）
にあり、この文書は数字の側だけを扱います。

**読み方**: §1 が結論、§2〜§4 が前提です。**§5 は根拠となる測定の時系列記録で、通読は不要**です
（撤回した解釈も経緯ごと残してあります）。数字がまだ使えない節には見出しにタグを付けてあります。

**測定は 2 つのモードにまたがります**（本番の構造が途中で変わったため = ADR 0020）。見出しの
**【連続経済】**（§5.1〜§5.7）と**【シナリオ】**（§5.8〜）は world の作り方も初期配布も違うので、
**タグをまたいだ数字は比較できません**。対照表は §4 の冒頭にあります。

## 1. 結論

| 指標 | 評価 | 決め手 |
|---|---|---|
| **M9** `mean − λ·std` | **◎**（λ と epoch 長の組を決める条件付き） | 幸運なレバレッジを 2 位 → 9 位に打ち消す（§5.7）／ 破綻を `random` の 13 倍罰する（§5.5）／ 絶対スケールを保つ（§5.4）／ noop が厳密に 0（§5.1） |
| **M4** 超過対数成長 | **△** | 病的挙動は無いが、**幸運なレバレッジ週を 2 位に置く**（§5.7）。リスクを見ない代償 |
| **M1** 損益額 | **△** | M4 と同じ欠陥。加えてベンチマーク相対でないぶん劣る |
| **M7** MPPM | **✕**（この環境では） | ρ を 2 → 20 にしても **M1 と同一順位**。パラメータを増やす代わりに得るものが無い |
| **M13** Sharpe | **✕**（主指標として不可） | **週 +26 が週 +4,890 に勝つ**（§5.4）。上昇週でも +260 の参加者を 1 位に置く（§5.7） |
| **M27** Borda | **○**（seed 横断の集約としてのみ） | 集約として健全に機能。1 run の指標ではない。キングメーカー問題は未検証 |

**λ = 0.25 は高すぎます。** この環境で最も稼ぐ戦略（週 +4,000、週次 Sharpe 約 1.28）を最下位に落とします。
epoch = 12 ブロックなら **0.15 前後**が、稼ぐ戦略を残しつつ「ばらつきの割に稼げない」戦略を下に置く、
という当初の意図どおりに働きます（§5.3 §5.4）。

**指標の選択に必要な測定は完了しています。** 残るのは λ と epoch 長の組をどこに置くかという判断で、
これは測定では決まりません（§5.6 のとおり、両者は交換可能なノブです）。

> **2026-08-19 追記 — 上の結論はすべて「連続経済 1 本」での測定です。** ADR 0020 が本番を
> `scenario` モードに変えたため、この表は本番の前提に対しては未確認になりました。シナリオモードでの
> 初測定は **§5.8**（7 レジーム × 3 seed = 18 シナリオ）で、そこで分かったのは 2 点だけです:
> **① 15 通り（5 指標 × 3 集約）が上位 4 体・下位 3 体で一致し、食い違いは「noop と区別がつかない」
> 集団の中だけ。② λ = 0.25 はここでは稼ぎ頭を落とさない**（§5.3 では落とした = λ はモードをまたげない）。
> **指標の選択はシナリオモードでは未確定**で、決め手になる中位層が空だったのが理由です（§5.8 (f)）。
>
> **2026-08-23 追記 — 中位層を入れて再測定しました（§5.9）。** 在庫を配らず買わせるようにしたところ
> `lp-provider` が全 21 シナリオで稼働し、**指標が初めて食い違いました**: M4 は 21/21 シナリオで黒字の
> この参加者を 3 位に置き、**M9（λ=0.25）は 8 位（何もしない参加者より下）に落とします**。
> 1 epoch あたり Sharpe 0.2454 が λ = 0.25 のほぼ真上にあるためで、λ = 0.15 なら 3 位に戻ります。
> **λ の選択がそのまま「小さく確実に稼ぐが在庫を抱える戦略の順位」になる**、というのが現状です。

## 2. 前提: 競技と採点の仕組み

競技は運営が制御する devnet 上で行います（参加者数百人・期間 1 週間）。参加者は自分のプログラムを
走らせ、AMM・レンディング・永久先物・CDP といった DeFi プロトコルを相手に取引します。運営は価格の
基準値を配信し、イベント（暴落・流動性の引き抜き・ステーブルコインのデペグなど）を注入します。

> **world の作り方は 2026-08-19 に変わりました（ADR 0020）。** 本文書の §5.1〜§5.7 は
> 「**1 本の連続した経済**を非公開スケジュールで走らせる」前提で測っています。本番はその後
> **シナリオモード**（(regime, seed) ごとに world を作り直し、レジーム等重みで集約する）に決まり、
> イベントは非公開スケジュールではなくレジーム YAML のレンジと seed が決めます。以下の採点式の
> 説明はどちらのモードでも同じで、**違うのは「1 world あたりの epoch 数」と「集約が要るかどうか」**です。

採点は、**一定間隔（= epoch。本番は 4 時間 × 42 回、検証環境では 12 ブロック × 41〜42 回）で全員の
資産価値を測り**、隣り合う断面の**対数リターンからベンチマークの同じ期間のそれを引き**（= 超過リターン
`x_e`）、その平均からばらつきの λ 倍を引く、という手順です。

```
score = mean(x_e) − λ × std(x_e)          λ = 0.25（暫定）
```

**ベンチマーク**は「何もしない参加者」（`noop`）です。実在のエントリで、他の参加者と同じ初期配布を
受け取り、一切取引しません。差し引く相手が実在のエントリであることが重要で、**全員が等しく持たされて
いる資産の値動き（例: ガス代用の ETH）が自動的に打ち消えます**。

λ の意味は「**何もしないのを上回るために必要な、1 epoch あたりの最低リターン／リスク比**」です。
何もしない参加者は超過リターンが常に 0 なので、スコアもちょうど 0。したがって `mean/std > λ` を
満たさない参加者は、**利益が出ていてもスコアが負**になり「何もしなかった人」より下の順位になります。
これが本文書の主要な論点です。

> 以降の表では 1 epoch あたりの値を指数表記で書きます（`1e-4` = 0.01%）。`mean/std` はその参加者の
> 1 epoch あたり Sharpe 比で、λ はこの値に対する閾値です。run 全体では `mean/std × √epoch数`
> （41 epoch なら約 6.4 倍）が週次 Sharpe になります。

## 3. 候補の指標

| 記号 | 式 | 一言 |
|---|---|---|
| **M1** | 期末資産 − 期初資産 | 単純な損益額。リスクを一切見ない |
| **M4** | `ln(期末資産 / ベンチマークの期末資産)` | ベンチマークに対する複利成長率。終点だけを見る |
| **M7** | MPPM（Goetzmann et al. 2007） | 「リスク調整済み指標のゲーム化」対策として提案された学術指標。リスク回避度 ρ を持つ |
| **M9** | `mean(x_e) − λ·std(x_e)` | **ADR 0019 が採用**。経路のばらつきを罰する |
| **M13** | `mean(x_e) / std(x_e)` | Sharpe レシオ。比率なので「小さく安全に」が最適解になり、主指標には不適 |
| **M27** | 各 run の順位を合計（Borda） | 順位だけを使う。run ごとのスケール差に強い |

記号は設計側の指標カタログの通し番号です。M9 が選ばれた理由は「連続経済 1 本の上で使えること」と
「経路のばらつきを罰する項が内在すること」で、詳細は ADR 0019 にあります。**前者は ADR 0020 で消えました**
（本番がシナリオモードになり、複数 world を要求する M4 Gauntlet / M27 Decathlon が構造的に成立するため）。
M9 は暫定既定として維持されていますが、選択そのものは再比較にかかっています（§5.8）。

## 4. 測定に使った環境・参加者・run

検証は Anvil（ローカルのイーサリアム実行環境）に全プロトコルをデプロイした状態で行い、
本番と同じプログラム（環境デーモン・採点器・参加者ランタイム）を使います。

### 測定は 2 つのモードにまたがる（混ぜて読めません）

本番の構造が途中で変わりました（ADR 0020）。**§5.1〜§5.7 と §5.8 では world の作り方も初期配布も
違う**ので、節をまたいだ数字は比較できません。以下の §4 の残りは、断りがない限り**連続経済側**の条件です。

| | **連続経済**（§5.1〜§5.7） | **シナリオ**（§5.8〜） |
|---|---|---|
| world | 1 本を通しで走る | (regime, seed) ごとに作り直す |
| 長さ | 504 ブロック = 41〜42 epoch | 1 シナリオ 360 ブロック = 29 epoch |
| 本数 | 1 run = 1 世界（seed 違いで反復） | 18 シナリオ（7 レジーム × 3 seed、うち 3 本は失敗） |
| レジーム | `b-harness` / `ruin-test` / `lucky-drift`（指標を測るための専用） | `metric-*`（公式レジームの市場条件） |
| **初期配布** | 1 ETH + 100,000 USDC + **20 WETH** | 1 ETH + 100,000 USDC + **WETH 無し**（ADR 0019 §6 の USDC-only） |
| 集約 | 無し（1 本なので） | レジーム等重み。`zscore` / `borda` / `mean` の 3 候補を総当たり |
| 該当する結論 | §1 の表 | §1 の追記と §5.8。**指標は未確定** |

配布の違いは意図的ではなく**経緯**です。連続経済側は §5.3 で 20 WETH を足しました（在庫が無いと
裁定戦略が機会を落とすため）。シナリオ側は ADR 0019 §6 の宣言どおり USDC-only に戻しました。
その代償が §5.8 (f) で、**在庫を持って待つ `lp-provider` が一度も取引しません**。

**イベント**: 検証用の 1 週間（`config/regimes/b-harness.yaml`）には 3 種類・6 つの窓があります。

| 窓 | 数 | 内容 |
|---|---|---|
| デペグ | 3 | ステーブルコイン DAI が $1 を割る。環境が売って押し下げ、窓が閉じると買い戻す。**うち 1 つは戻らない** |
| 価格ドリフト | 2 | 参照価格が一方向に引かれ、平均回帰も弱まる。**うち 1 つは水準が戻らない**（再評価） |
| フロー偏り | 1 | 全取引所の注文フローが同じ方向に傾く |

別に、破産を起こすための `ruin-test`（暴落を追加）と、レバレッジに有利な `lucky-drift`（ドリフトを
上昇に固定）という**指標を測るための run 専用**のレジームがあります。

**参加者**（測定の過程で 4 体 → 11 体に増やしました）:

| id | 何をするか |
|---|---|
| `noop` | 何もしない。ベンチマーク |
| `peg-arb` / `-eager` | DAI が安くなったら買い、$1 近くで売る。eager は浅い割安で買い par まで粘る |
| `peg-arb-small` / `-big` | `peg-arb` と同一コードで**売買サイズだけ** 5% / 10% |
| `venue-arb` / `multi-arb` | 複数の取引所間の ETH 価格差を取る。**互いに独立実装** |
| `lp-provider` | 流動性を提供して手数料を得る（**在庫を持って待つ**唯一の型） |
| `random` | ランダムに売買する（**下限の対照**） |
| `levered-long` / `-max` | 担保を入れて借り、より多くの ETH を持つ（目標 HF 1.8 / 1.05〜1.15 = 約 4.5 倍） |

**初期配布**（連続経済側。シナリオ側は上表のとおり WETH 無し）: 1 ETH（ガス代用）+ 100,000 USDC +
**20 WETH**。WETH は §5.3 で追加しました。デペグする DAI は配りません（買って初めて持てるようにするため）。

> **初期配布の対照実験**（旧配布 100 ETH + 25,000 USDC = 資産の 92.3% が ETH／新配布 = 2.9%）。
> 生のリターンで採点していた頃は旧配布の 4 体が全員 −0.02 前後に潰れ、「旧配布では λ が参加者を
> 区別できない」と解釈していましたが、**これは配布の性質ではなく §5.1 の実装漏れの結果でした**。
> 新配布を採る理由は別にあります: ベンチマークが 92% ETH のポートフォリオだと「ベンチマークに対する
> リスク」と「リスク」が別物になり、ETH を売ること自体がベンチマーク比の空売りとして測られます。

## 5. 測定の記録（時系列）

**§5.1〜§5.7 は【連続経済】、§5.8 以降は【シナリオ】**です（§4 の対照表）。world の作り方も初期配布も
違うので、タグをまたいだ数字は比較できません。同じタグの中でも run ごとに条件が変わります。

### 5.1【連続経済】ベンチマークの差し引きが抜けていた

当初の実装は超過リターンではなく**生のリターン**を採点していました。5 seed の測定でこれが露見しました。

生のリターンで採点すると、**何もしない `noop` のばらつきが 2.22e-4** あり、これは実際に取引していた
`peg-arb` の全ばらつき 2.38e-4 の **93%** を占めていました。**全員が等しく持たされているガス代用の
ETH が値動きしていただけ**で、λ は参加者のリスクではなく配布物の値動きを測っていたことになります。

差し引きを入れた前後（5 seed の `mean/std` の平均）:

| 参加者 | 生のリターン | **超過リターン（正しい定義）** |
|---|---|---|
| peg-arb-eager | 0.281 | **0.358** |
| peg-arb | 0.111 | **0.241** |
| venue-arb | 0.051 | 0.070 |
| noop | 0.022（ばらつき 2.22e-4） | **0.000（ばらつき 厳密に 0）** |

`peg-arb` のばらつきは 2.38e-4 → 9.08e-5 に落ちます。残った分がこの参加者自身のリスクです。
**この再計算に run のやり直しは不要でした**（各断面の生の資産価値を保存する設計にしてあったため）。

### 5.2【連続経済】λ = 0.25 は「何もしない」を黒字参加者の上に置く

5 週間分の順位を合計した値（M27 Borda。小さいほど上位）:

| 指標 | 1 位 | 2 位 | 3 位 | 4 位 |
|---|---|---|---|---|
| M1 損益額 / M4 / M7 | eager=5 | **peg-arb=11** | venue-arb=17 | noop=17 |
| M13 Sharpe | eager=5 | **peg-arb=10** | noop=17 | venue-arb=18 |
| **M9（採用案、λ=0.25）** | eager=5 | **noop=12** | peg-arb=16 | venue-arb=17 |

**M9 だけが「何もしない参加者」を、確実に利益を出した参加者より上に置きます。** 他の 4 指標は 5 週すべてで
`peg-arb`（週あたり +92〜+165 USDC の黒字）を `noop` の上に置き、M9 は 5 週中 3 週で下に落とします。
これは ADR 0019 が自ら掲げた基準（**何もしない参加者は、まともな参加者の中位より下に来るべき**）を
満たしていません。

原因は `peg-arb` の `mean/std`（seed 別に 0.174 / 0.251 / 0.237 / 0.245 / 0.300）が λ=0.25 をまたいで
いることで、λ を 0.15 まで下げると M9 の順位は M1 と完全一致します。**指標の族が悪いのではなく、
閾値 λ の較正の問題です**（λ の刻みごとの順位は、条件の良い run でやり直した §5.3 の表を見てください）。

**イベントの種類を増やしても構図は変わりませんでした。** これまで「run 全体の設定」でしか表現できな
かった 2 つのレジームを窓イベント化し（`cexDrift` / `flowTrend`）同じ 5 seed を回し直しましたが、
`peg-arb` は依然 λ=0.25 をまたぎ（2/5）、順位合計でも「何もしない」が 2 位のままでした。

**そして `venue-arb` は 5 seed 中 3 本で一度も取引しませんでした。** 原因は当人のログにあり、
機会の不足ではありませんでした:

> `the widest gaps need inventory this agent does not hold`（513 ラウンド中 503 回）

取引所間の価格差を取る戦略は、高い方で売って安い方で買うために ETH の在庫が要ります。当時の初期配布は
USDC のみだったので、価格差が逆向きに開いた seed では何もできませんでした。**これは配布の制約であって、
環境の機会不足でも戦略の欠陥でもありません。** そして §5.1 でベンチマークの差し引きを入れた結果、
**全員が等しく持っている資産の値動きは自動的に打ち消える**ので、この制約はもう不要でした。

### 5.3【連続経済】λ = 0.25 は、この環境で最も稼ぐ戦略を落とす

全員に 20 WETH を配ったところ **`venue-arb` の取引数は 0〜16 → 274〜296、損益は 0〜250 → +3,400 台**に
なりました。在庫が無いから動けなかったという読みは裏付けられ、しかも「動ければ最も稼ぐ戦略」でした。

### 5.5【連続経済】レバレッジと破産（前半の数字は【無効】）

G1（破産フロア）と G2（採点上の凍結）を実データで動かすため、**破産させるための run** を 2 本
組みました（`config/regimes/ruin-test.yaml`）。目標 HF を 1.05（約 5 倍）に上げ、**22〜28% の暴落**を
注入し、2 本目では 1 ラウンドの上限も 4 倍にしました。**どちらも破産せず**、レバレッジも 1.87 倍しか
積み上がりませんでした。当初これを「1 ラウンドの上限が実質的なレバレッジ上限になっている」と解釈し
ADR にもそう記録しましたが、**その帰属は誤りでした**:

```
submitted 19 / submit_failed 483
480x Execution reverted: panic: arithmetic underflow or overflow (0x11)
```

**借入の 99% が revert していました。** Aave の USDC 流動性は、ローカルデプロイでは run 開始時に admin が
供給する **100,000 USDC** だけです（`sdk/src/protocols/aave.ts` の `LOCAL_FLASH_LIQUIDITY_USDC_UNITS`）。
レバレッジ 2 体と Aave フロー 4 体が借りると枯渇し、以降の借入は全て失敗します。しかもこの実装では
**エラーが算術オーバーフローとして出る**ため、原因がメッセージから読み取れません。

したがって **§5.4 の `levered-long` 系の損益は「レバレッジの結果」ではありません**（Aave を使わない
8 体の結果は影響を受けません）。**副次的な観察**として、暴落を含む週では b-harness の稼ぎ頭だった
venue 間裁定の 2 体が**損失に転じました**（−932 / −24）。価格が動き続ける局面では、裁定の取り逃しと
逆行が利益を上回るということです。これは Aave と無関係なので有効な観察です。

借入可能 USDC を **100,000 → 2,000,000** に上げました（定数 1 行。run 開始時に cheatcode で供給される
ので state dump の焼き直しは不要）。

### 5.6【連続経済】λ と epoch 長は独立したノブではない

保存済みの毎ブロック価値から epoch 長だけを変えて採点し直しました（run のやり直し不要。ただし
G7 の median は掛からないので live マークでの比較です）。

| epoch 長 | epoch 数 | `lp-provider` の Sharpe | `multi-arb` の Sharpe | λ=0.25 での 1 位 |
|---|---|---|---|---|
| 6 ブロック | 83 | 0.377 | 0.141 | `lp-provider`（週 +26） |
| **12 ブロック** | **41** | 0.615 | 0.215 | `peg-arb-eager` |
| 24 ブロック | 20 | 0.988 | 0.288 | **`multi-arb`（週 +4,890）** |
| 48 ブロック | 10 | 1.277 | 0.368 | **`multi-arb`** |

**epoch を長くすると Sharpe は全員上がります**（平均は期間長に比例し、ばらつきは平方根でしか増えない
ため `mean/std ∝ √期間`）。その結果 λ という**固定の閾値の意味が、epoch 長で変わります**。関係は近似的に
`実効的な厳しさ ≈ λ / √(epoch 長)` なので、**λ を 0.6 倍にすることと epoch 長を約 2.8 倍にすることが
等価**です。λ = 0.25 のままでも epoch を 12 → 24 ブロックにすれば順位は「稼ぎ頭が 1 位」になります。

**したがって λ を単独で決めることはできません。** 決めるべきは「λ と epoch 長の組」で、どちらを動かすかは
別の基準で選ぶことになります（epoch を長くする = 判断の粒度が粗くなるが「たまたま何もなかった epoch」の
割合が減る／λ を下げる = 粒度は保つがばらつきへの罰が弱まる）。§1 で λ = 0.15 を推奨したのは
**epoch = 12 ブロックでの推奨**であり、本番が 4 時間 epoch を採るなら読み替えが要ります。

ADR 0019 §2 は、市場のドリフトが平均項に残ることを既知の限界として挙げ「**幸運なレバレッジ週が
報われる**」と書いています。ドリフトの方向は seed が引くため測れていなかったので、**上昇方向に固定した

再現: `npm run backtest -- --scenarios config/scenarios/metric-boxA.yaml --agents config/rosters/metric-field.yaml`
（+ `metric-boxB.yaml`）→ `npm run metrics -- --matrix runs/matrix-<id>`

**(h) 対応: 在庫は配らず、買わせることにしました（2026-08-23。再測定は未実施）。** (f) の空の中位層に対して
配布を変える（WETH を配る）案もありましたが、採らなかったのは**配られた β と買った β が別物**だからです。
配られた在庫はベンチマークも同じだけ持つので全員のスコアから打ち消え、代わりに誰も選んでいない
エクスポージャーが混ざります。買った在庫はスプレッドを払って選んだポジションで、現金のベンチマークに
対する**その参加者自身のリスク**として `std_e` に乗り、λ 項が値付けます。**中位層はここから生まれます。**

- `lp-provider` — mint の直前に、片側の脚に足りるぶんだけ USDC で WETH を買うようにしました
  （範囲外で持つ WETH は手数料を生まない純粋な分散なので、早く買うことも多く買うこともしません）
- `venue-arb` — 全 venue が fair より高く売る在庫が無いとき、**venue 間スプレッドが往復コスト（80bps）
  を超える場合に限り**最安 venue で仕込むようにしました。超えないなら買わない = 素の β だからです
- **自己改善 LLM に action の語彙を渡すようにしました**（`ACTION_TYPES_BY_PROTOCOL`）。改訂プロンプトは
  現在の戦略コードしか手掛かりを与えていなかったので、**一度も swap したことのない戦略の LLM は
  `swap` の存在を知りようがありません**（存在しない名前を書けば設置前に弾かれる）。有効な venue の
  action 名を列挙し、「持っていないことは何もしない理由にならない」と明記しました

120 ブロック 1 シナリオの確認では `lp-provider` が 2 tx（WETH 購入 → mint）の後 116 ラウンド在庫を
抱えて **+33.47**、`venue-arb` は 117 tx で **+1,689**（測定時はそれぞれ 0 tx / 中央値 +22）。
**行列での再測定はこれからです。**

### 5.9【シナリオ】中位層を入れて再測定 — 指標が初めて食い違った

§5.8 (h) の変更（在庫は配らず買わせる）の後、同じ 21 シナリオを回し直しました（2026-08-23。
**21/21 成立** = 前回失った 3 本の setup tx タイムアウトは今回出ていません）。

**(a) 場が競争的になりました。**

| 参加者 | 平均損益（前回 → 今回） | 無取引シナリオ（前回 → 今回） |
|---|---|---|
| `lp-provider` | 0 → **+231**（中央値 +58） | **18/18 → 0/21** |
| `venue-arb` | +650 → **+3,326** | 6/18 → **0/21** |
| `multi-arb` | +15,596 → **+9,298** | 0 → 0 |

`multi-arb` の利益が 4 割減ったのは `venue-arb` が同じ裁定を取り合うようになったためで、
**首位が無競争でなくなりました**。

**(b) `lp-provider` が指標を分ける参加者になりました。** これが今回の中心です。

| | M4（リスク項なし） | M9（`mean − λ·std`、λ=0.25） |
|---|---|---|
| 平均値 | **+0.002497** | **−0.000045** |
| 正だったシナリオ | **21 / 21** | **5 / 21** |
| 順位 | **3 位**（全集約） | **3 位**（zscore）/ **8 位**（borda・mean。noop より下） |

**M4 では 21 シナリオすべてで黒字**なのに、M9 では 16 シナリオで在庫リスクがハードルを超えられません。
唯一まとまって勝てるのは `cex-drift` の 3 本（+0.00033〜0.00040）で、**トレンドのある相場でだけ
手数料が在庫リスクを上回る**という読み方ができます。1 epoch あたり Sharpe は **0.2454** で、
λ = 0.25 のほぼ真上に載っています。

**(c) したがって λ の選択が具体的な帰結を持ちました。** λ を 0.15（§1 の推奨値）に下げると `mean` 集約
では `lp-provider` が **8 位 → 3 位**に戻ります。**「小さく確実に稼ぐが在庫を抱える戦略は、
何もしないより上か下か」**という問いに、λ が直接答えている状態です。§5.3 §5.4 の λ 議論は連続経済で
「稼ぎ頭を落とすかどうか」でしたが、シナリオモードでは**中位層の生死**として現れます。

**(d) 集約の選択も効くようになりました。** M9 だけが 3 集約すべてで異なる順位を出します
（他の 4 指標は 2 通り）。`borda` は λ = 0.15 でも `lp-provider` を 8 位に置いたままで、これは
**21 中 16 シナリオで中位以下に沈む**ためです。平均は勝つが多数決では負ける、という形が
`mean` と `borda` を分けています。

**(e) #55 の露出**（1 体を抜いたときの場の sd 比）: M1 1.65 / M4 1.82 / M9 1.80（最悪 2.30 =
`multi-arb` / cex-drift#202）/ M7 1.83 / **M13 1.21**（最も低い）。前回（1.55〜1.82）と同水準です。

**(f) 残る限界**: `peg-arb` 系は依然として `metric-depeg` の 3 シナリオでしか動かず、11 体中 4 体が
実質 noop のままです。中位層は `lp-provider` 1 体で支えられており、**この 1 体が指標選択の全証拠**に
なっています。結論を出す前にもう 1 体、別の型の中位層（例えば手数料を取る別の形、あるいは
`peg-arb` に機会のあるレジーム配分）が要ります。

再現: `npm run backtest -- --scenarios config/scenarios/metric-boxA.yaml --agents config/rosters/metric-field.yaml`
（+ `metric-boxB.yaml`）→ 2 つの matrix.json を絶対パスで結合 → `npm run metrics -- --matrix <dir>`

> **運用メモ**: 1 台で matrix を 2 本回すなら間に掃除が要ります。anvil の `--load-state` は
> `~/.foundry/anvil/tmp/` に **1 マトリクスあたり ~20GB** の作業ディレクトリを作り、anvil 終了後も
> 消えません。48GB の golden AMI では 2 本目が `ENOSPC` で 9 中 7 シナリオを失いました

## 6. まだ測れていないもの

- **1 週間あたりのガス消費** — 取引ごとの消費ガス量も実効ガス価格も、どこにも記録されていません
  （記録されているのは優先手数料のみ）。得られる唯一の量は「504 ブロックあたり最大 55 取引」で、
  ガス代用 ETH をどこまで減らせるかの判断ができません
- **マーク操作対策（G7）の効果** — 各 epoch 境界の価格は、直前 5 ブロックの中央値を使います
  （1 ブロックだけプールを押して評価額を吊り上げる操作への対策）。中央値と当該ブロックの実価格の
  最大乖離は DAI で 54.9bps（9 境界）/ 20.6bps（41 境界）と記録されていますが、
  **「対策を掛けなかった場合のスコア」を保存していない**ため、順位への影響量が出せません

その他、測定中に判明した細かい問題: 504 ブロックの設定では epoch が 42 ではなく 41 になる
（採点窓が 503 ブロックのため）／ epoch 境界のブロックでは資産推移グラフ側にも中央値が入っており、
グラフは実価格・中央値は採点だけ、に分けるべき。

## 8. 再現方法

**連続経済**（§5.1〜§5.7）— run ディレクトリを並べる:

```
npm run metrics -- runs/<出力ディレクトリ> [...] [--lambda 0.25] [--rho 2] [--out metrics.json]
```

**シナリオ**（§5.8）— 行列ごと採点し、指標 × 集約の総当たりを出す:

```
npm run backtest -- --scenarios config/scenarios/metric-boxA.yaml --agents config/rosters/metric-field.yaml
npm run backtest -- --scenarios config/scenarios/metric-boxB.yaml --agents config/rosters/metric-field.yaml
npm run metrics -- --matrix runs/matrix-<id>
```

どちらも保存済みの `summary.json`（各 epoch 境界での参加者ごとの資産価値）を読み、上記の全指標で
採点し直します。チェーンへの接続も再実行も不要です。`--matrix` はこれに加えてシナリオ横断の集約
（`zscore` / `borda` / `mean`）と #55 の露出を出します。**モードが混ざった run 集合は拒否されます**
（ADR 0020 §1。1 world あたりの epoch 数が違うので比較にならないため）。
