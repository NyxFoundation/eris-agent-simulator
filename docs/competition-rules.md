# ASCON 競技規約（第1回）

> **本文書はドラフトです（2026年8月31日時点）。**弁護士による確認を受ける前のものであり、確定版ではありません。制定日、ご利用いただくサービスの構成、および「●」を付した数値は未確定です。公開時には、確定した内容に差し替えます。

本競技規約は、**ASCON 参加規約** 第1条第2項に基づき、ASCON 第1回大会の競技方式、評価指標および実行環境について定めるものです。本競技規約で定義しない用語は、参加規約の定義によります。

## 0. 用語の定義

### 0.1 本規約で定める用語

いずれも競技環境（主催者が運用するシミュレーション環境）の中の概念であり、現実の資産・市場を指しません。

| 用語 | 意味 |
| --- | --- |
| エージェント | 参加単位が提出する、自動で取引判断を行うプログラム |
| ブロック | 競技環境の時間と記録の最小単位。取引はブロックにまとめて記録されます。**2秒ごとに1ブロック**が確定し、1ブロックが1回の判断機会に対応します |
| エポック | **評価の単位。**全参加単位が同一の初期条件から開始し、所定のブロック数を実行して終了する1単位です。ライブ競技期間中に k 回実行され、各エポックの開始時に環境が初期化されます（§4.7.1） |
| 評価区間 | エポックを一定ブロック数ごとに区切った区間。スコア（§4.4）は、区間ごとの資産価値の系列から計算します |
| ラウンド | **評価区間の別称**です。主催者が提供するダッシュボードは、この語で表示します。**1ブロックのことではありません**（1つの評価区間は複数のブロックからなります） |
| シナリオ | 「レジーム」と「乱数シード」の組で定まる、1回の市場の再生。各エポックのシナリオは非公開セット（§3.3）から生成されます |
| レジーム | 市場条件の型（§3.2 の7種類）。それぞれ、環境が注入する価格変動・注文の流れ・イベントの生成規則を定めたものです |
| 乱数シード | 乱数の初期値。同一のシードであれば、環境側の価格の経路とイベントの発生が同一に再現されます |
| 参照価格 | 環境が生成し、競技環境内で毎ブロックの冒頭に配信する基準価格。すべてのエージェントが同じ条件で読み取れます。更新は各ブロックの先頭で処理されるため、**エージェントが観測できるのは1ブロック前の値**です（§2.6） |
| 観測データ | 各ブロックの確定後にエージェントへ渡される、市場と自己資産の状態データ（observation）。JSON で受け取ります |
| アクション | エージェントが返す取引の指示（トークンの交換、貸し借り、注文など）。SDK が定める形式に従います |
| バンドル | 複数のアクションを1つのトランザクションとして不可分に実行する送信形式。1本のトランザクションとして数えます（§2.6） |
| 戦略の改訂 | 大規模言語モデルが、一定ブロック数ごとに、走行中の戦略コードそのものを書き換えること（§2.5）。毎ブロックの取引判断とは別の経路です |
| ベンチマーク | 初期資本を一切動かさない参照エージェント（§4.3）。スコアの基準点になります |
| 評価グループ | 同一の競技環境に同時に投入され、同じ市場を通じて互いに影響し合う参加単位の集まり（§3.4）。本規約では、単に「グループ」ということがあります |
| SDK | 主催者が公開する、エージェント開発用のライブラリ・テンプレート一式 |

### 0.2 一般的な用語の補足

ブロックチェーン・DeFi（分散型金融）の一般用語のうち、本規約の理解に必要なものです。ブロックチェーンに馴染みのない方は、まずこの表からお読みください。

| 用語 | 意味 |
| --- | --- |
| ブロックチェーン | 取引の記録を「ブロック」という単位にまとめ、鎖状につなげて保存する台帳の仕組み。競技環境はこの仕組みの上に構築されています |
| トランザクション | 台帳に記録される1件の取引指示。エージェントのアクションはトランザクションとして送信され、ブロックに取り込まれて初めて成立します |
| スマートコントラクト | ブロックチェーン上で自動的に実行されるプログラム。本競技の取引所や貸し借りの仕組みは、すべてスマートコントラクトとして動いています |
| トークン | ブロックチェーン上で残高が管理される資産の単位 |
| ガス／優先手数料 | トランザクションの処理手数料。優先手数料（priority fee）は、ブロック内の処理順を上げるために上乗せする部分です |
| AMM | 自動マーケットメイカー。利用者が資産を預け合った「プール」を相手に売買する形式の取引所で、価格は預かり残高から自動的に決まります。プールに資産を預けて取引手数料の分配を得ることを**流動性提供**と呼びます |
| レンディング | 資産を担保に別の資産を借りられる貸し借りの仕組み。担保の価値が不足すると、担保が強制的に売却されます（**清算**） |
| パーペチュアル | 証拠金（担保金）を預けることで、自己資金より大きな金額の売り・買いポジションを持てる取引（無期限先物）。損失が証拠金に比べて大きくなると清算されます |
| リキッドステーキング | ETH を預けて利回りを受け取りつつ、その預り証にあたるトークン（LST）を市場で売買できる仕組み。**同じ資産に「Vault が保証する償還レート」と「市場が今払う価格」の2つの価格が並存する**のが特徴です |
| ステーブルコイン | 特定の資産（主に米ドル）と等価であることを企図したトークン。基準価格からの乖離を「デペッグ」と呼びます |
| 裁定 | アービトラージ。同じものに複数の価格が付いているとき、安い方で買い高い方で売って差額を取る取引 |
| USDC / ETH / WETH | 競技環境内で発行される資産。USDC は米ドル相当のステーブルコイン、ETH は環境の基軸通貨（ガスの支払いにも使います）、WETH は ETH をトークンの形に包んだものです。いずれも**競技環境の外では一切の価値・交換性を持ちません** |

## 2. 提出と実行

### 2.1 提出形式

第1回大会の提出形式は、**運営ホスト型の1形式のみ**です。参加者が自らインフラを用意する必要はありません。

提出していただくものは次の2つです。

|  | 内容 |
| --- | --- |
| **エージェント一式（ZIP ファイル）** | 競技環境の状態（観測データ）を JSON で受け取り、行動またはトランザクションの意図を返す、SDK 準拠のプログラム。依存関係を含めて1つの ZIP にまとめてください |
| **参加者認証情報** | エージェントが利用する推論サービスが**認証を要する場合に限り**、その API キー等。参加規約 第8条の2 に従って取り扱います（認証不要のサービスや自前運用では提出は不要です） |

- 主催者は、**ブロックごとに1回**、提出物を呼び出します
- **提出されたエージェントは、主催者が管理するサーバー上で、全参加単位が同時に開始する形で実行されます**

> 💡 自前のインフラでエージェントを稼働させる形式（Remote Gateway 型）は、第1回大会では提供しません。第2回以降で導入を検討します。

### 2.2 提出の差し替え

- 提出期間中、**1日あたり5回まで**提出を差し替えることができます。**1日の起算は日本標準時の午前0時**とし、主催者のシステムが提出を受理した時刻を基準とします
- 形式上の要件を満たさず受理されなかった提出は、前号の回数に算入しません
- **最終評価の対象とする提出を2つまで選択**できます
- **選択しなかった場合、公開シナリオにおけるスコアの上位2件を自動的に選択します。**公開シナリオのスコアが同一の提出が複数ある場合は、**受理された時刻が早いもの**から順に選択します
- **最終評価の対象となる提出の数に応じて、次のとおり評価します**

| 対象となる提出の数 | 評価 |
| --- | --- |
| **2件** | それぞれ独立に非公開セットで評価し、**スコアの高い方**を当該参加単位の最終スコアとします。両者を平均することはありません。2件のスコアが同一の場合、**受理された時刻が早い方**を最終スコアの根拠とします |
| **1件** | 当該1件のスコアを最終スコアとします |
| **0件**（有効な提出がない場合） | 当該参加単位は最終ランキングの対象外とします。この場合、賞金の取扱いは参加規約 第20条第2項によります |

- **提出期間の終了をもって、提出物（初期戦略コード・改訂機構・設定）は凍結されます。**以後、参加者による変更はできません。**なお、凍結された改訂機構が実行中に行う戦略コードの自己改訂（§2.5）は、競技の一部として引き続き発生します**

### 2.3 実行環境

| 項目 | 内容 |
| --- | --- |
| 計算資源 | **2 vCPU / メモリ 4 GB を上限**とします。**割り当ての保証ではなく、これを超えないための制限です。**エージェントのプロセスは、他の参加者のエージェントと計算資源を共有します |
| 応答タイムアウト | **5,000 ミリ秒** |
| タイムアウト・異常終了時 | 当該ブロックは行動なし（no-op）として扱い、自動的に再起動します |
| 再起動の上限 | **1エポックあたり3回**。これを超えた場合、当該エポックにおいて凍結します（凍結の採点上の効果は §4.4.2・§4.5 によります） |
| ブロック生成との関係 | **ブロックは定刻で確定します。**エージェントの応答を待って遅らせることはありません。応答が間に合わなかった場合、そのブロックは行動なしとして扱い、当該エージェントのトランザクションは次のブロック以降に繰り越されます |
| 外部通信 | エージェントのプロセスは外部ネットワークへ**接続できます**（自前の推論サービス等を利用するため。2026-09-04 決定）。ただし**ブロックチェーンへのアクセスは主催者の RPC ゲートウェイ経由に限られ**（cheatcode は拒否されます）、**他の参加者のプロセスや主催者の内部系へは接続できません** |

### 2.4 決定論と再現

- エージェント内部で乱数を用いる場合、**起動時に主催者が渡すシードから導出**してください
- 同一のシード、同一の提出物（初期戦略コード）、および**各改訂版の戦略コードとその適用ブロック（版の切替記録）**により、すべての評価を再実行できる状態を維持します。**取引判断のコード（`decide()`）は、観測（observation）およびシード由来の乱数のみに基づく決定論とし、外部通信・時刻その他の非決定的な入力に依存してはなりません**（外部通信および自前推論は、取引の判断経路の外にある改訂ループで行います）
- 取引の判断は**決定論的なコード（`decide()`）**が行い、推論はそのコードを一定ブロックごとに書き換えるだけです（§2.5・クリティカルパス外）。したがって評価の再生は、**記録されたシードと、各時点で実行されていた戦略コード（初期版および各改訂版のソース）を再実行する方法**により、決定論的に行います。**主催者は、ライブ競技において各改訂で生成された戦略コードを記録します**（推論そのものの応答の再生には依存しません）
- **どのモデルを用いるかは参加者が選択します**（自前の大規模言語モデルを含みます）。主催者は、参加者が用いたモデルの名称およびバージョンを記録します
- **推論はブロック生成のクリティカルパスに入りません**（§2.5）。したがって、推論の遅延がブロックタイムに影響することはありません

### 2.5 推論 — 大規模言語モデルの役割

**重要：大規模言語モデルは、各ブロックの取引判断を行いません。**

|  |  |
| --- | --- |
| **各ブロックの取引判断** | **参加者が提出したコード（`decide()`）が行います。**呼び出されてからミリ秒で応答することが期待されます。ここに推論は入りません |
| **大規模言語モデルの役割** | **一定のブロック数ごとに、現在の戦略のソースコードと、それまでの取引の記録および損益を受け取り、戦略のコードを書き換えます** |
| **呼び出しの頻度** | **1エージェントあたり、`reviseEveryBlocks`（既定 60）ブロックに1回**を上限とします。参加者はこの値を提出物の中で指定できます |
| **ブロック生成との関係** | **推論はブロック生成のクリティカルパスに入りません。**推論の実行中も、エージェントは既存の戦略で取引を継続します |

> 💡 エージェントは「毎ブロック、モデルに何をすべきか尋ねる」ものではありません。**毎ブロック取引するのは決定論的なコードで、モデルはそのコードを定期的に改訂する**という構造です。この設計にしているのは、毎アクションを推論に委ねると、実測で8〜28ブロックに1回しか判断できず、コードで書いた戦略の1/64の行動数しか出せなかったためです。

**認証情報と費用**

- 推論に認証が必要な場合は、**参加者が提出した参加者認証情報**を用います（参加規約 第8条の2）。認証不要のサービスや自前運用では提出は不要です
- **推論は、参加者が指定する推論サービス（自前の大規模言語モデルを含みます）を用います。**呼び出しは参加者のエージェント自身が行い、**主催者は共有の推論プロキシを提供しません**（2026-09-04 決定）。エージェントは外部へ接続できます（§2.3）
- **利用により生じる費用は参加者の負担です。**主催者は費用の額について責任を負いません
- 参加者は、**利用額の上限その他の制限を自ら設定できます。**制限により改訂が実行できなかった場合でも、主催者は再実行や補償を行いません。この場合、エージェントは既存の戦略で取引を継続します
- **提出された**参加者認証情報について、主催者は**当該参加者のエージェントの実行にのみ使用**し、他の情報と分離して保管します。**本大会の終了後速やかに削除します**

**呼び出し回数の目安**

1エージェントあたりの呼び出し回数は、おおよそ次の式で定まります。

```
呼び出し回数 ≒ エポック数 k × 1エポックあたりのブロック数 ÷ reviseEveryBlocks
```

**k と1エポックあたりのブロック数は、提出期間の開始までに公表します**（§7.1）。費用は選択したモデルと提供サービスの価格によります。**上限の設定を強くおすすめします。**

**対応するサービス**

**参加者は用いる推論サービスおよびモデルを自ら選択できます**（自前の大規模言語モデルを含みます）。主催者が受け付ける指定方法（エンドポイントおよび認証情報の形式）とその制約は、**提出期間の開始までに公表します**。

### 2.6 トランザクションの取扱い

| 項目 | 内容 |
| --- | --- |
| ブロックタイム | **2秒**。1ブロックが1回の判断機会に対応します（評価の単位である「評価区間＝ラウンド」は複数ブロックからなります。§0.1） |
| ブロック内の順序 | 到着時刻ではなく、**優先手数料の高い順**（オークション）で決定します |
| 1エージェントあたりの本数上限 | **1ブロックにつき3本**（バンドルを含みます）。これは環境の処理能力に由来する制限であり、取引の規模に対する制限ではありません（次項） |
| 1件あたりの発注規模 | **上限を設けません。**交換・貸借・建玉のいずれについても、金額・数量の上限はありません。1件の取引を制約するのは、**自己の残高**と、**取引先となる市場の厚み**（大きく出すほど不利な価格で約定します）だけです |
| ブロックガスリミット | **320,000,000 gas** |
| 1件あたりのガス上限 | **30,000,000 gas。**超えるトランザクションはゲートウェイが受け付けません |
| 1エージェント1ブロックあたりのガス上限 | **90,000,000 gas**（＝本数上限3本 × 1件あたりの上限） |
| 締切 | ブロック N に含まれるには、N のビルド開始までにゲートウェイに到達している必要があります。遅延して到着したものは次のブロックに繰り越します |
| 参照価格の更新 | 環境の参照価格更新トランザクションは、**各ブロックの先頭**で処理されます。その結果、エージェントが観測する参照価格は**1ブロック前の値**になります。この遅れはすべてのエージェントに等しく作用します |

> 💡 上表の値は**負荷試験を踏まえて確定しました**（ブロックタイム2秒・順序は優先手数料の高い順。§2.6.1）。順序を到着時刻で決めないのは、ネットワーク遅延や呼び出し順による有利不利をなくすためです。
>
> 💡 **ガスに上限を設けるのは、規模の話ではなく容量の話です。**上の「本数」の制限は環境の処理能力に由来しますが、本数だけではブロックを占有できてしまいます。参加者が自らのスマートコントラクトを配置できるようになったため（§3.1）、意図的に高価なコードへの1回の呼び出しでブロックガスリミットを使い切り、**他の参加者と、環境自身の参照価格更新**を締め出すことが可能になりました。これは対戦相手に対する行為ではなく競技基盤に対する行為であり、§8 の禁止行為です。
>
> 💡 **発注規模に上限を設けないのは、規模の判断を競技の一部とするためです。**上限があると、その値がそのまま「1回に出すべき量」になり、資産の何割を1つの機会に賭けるかという判断が競技から失われます。上限がない環境では、大きく出すことは板を自分で不利な方向へ動かすことでもあるため、**規模の選択それ自体が損益に表れます。**

### 2.6.1 ブロックタイムおよび順序決定方式の確定

**負荷試験を踏まえ、次のとおり確定しました（2026-09-04 決定）。**主催者は**提出期間の開始（2026年9月23日）に公表**し、**それ以降は変更しません。**

| 項目 | 確定値 |
| --- | --- |
| ブロックタイム | **2秒** |

## 4. 評価

### 4.1 資産評価

- 評価の基準通貨は **USDC** です。USDC は計算単位として常に $1 と扱います（他のステーブルコインには適用されません）
- エージェントの資産価値は、次のすべてを時価で合計したものです
    - ETH の残高および環境が価格を提供する全 ERC20 残高
    - AMM の流動性提供ポジション（未回収の手数料を含みます）
    - レンディングの担保評価額から負債評価額を差し引いた額
    - パーペチュアルの証拠金および未実現損益
    - リキッドステーキングのポジション
- 環境が価格を提供しないトークンは評価額に**算入しません**（0 と評価します）。ただし保有は記録され、評価結果とともに報告されます
- **環境が評価できないコントラクトの中に残った価値は、評価時点で 0 と評価します。**ただし、そのコントラクトを**通り抜けた**損益は満額算入します。例: ブロック100で10,000 USDC を預け、ブロック500に11,000 USDC を引き出した場合、+1,000 USDC は算入されます。算入されないのは、**評価時点でまだ中にあるもの**だけです
- **参加者が発行したトークンは、発行者・保有者のいずれに対しても 0 と評価します。**そのトークンを含む流動性提供ポジションは、**プールが保有する既知の資産に対する持分**として評価します
- **レンディングのポジションは額面ではなく回収可能額で評価します。**供給ポジションは、その市場に実際に残っている貸出トークンと、**環境が価格を提供する担保**のうち債務を裏付けている分に対する持分として評価します。借入ポジションは `max(0, 担保評価額 − 債務評価額)` とします。**市場が指定するオラクルは清算の判定にのみ用い、評価には用いません**
- 基軸資産（WETH 等）の評価には参照価格を用います。**ステーブルコイン等、市場でのみ価格が付く資産の評価には、当該市場に対する売り・買い両方向の実効価格の幾何平均**を用います
- **評価時点における市場由来の価格は、当該時点を含む直前5ブロック（付録A）にわたる値の中央値**をとります

> 💡 **中に残った価値を 0 とするのは、未知のコントラクトを評価しないためです。**評価しようとすれば、その評価はコントラクト自身の申告に依存し、申告は偽造できます。一方で「未検証のものには一切触らない」が常に最適になってしまうと、判断が競技から失われます。**通り抜けた損益を満額算入する**ことでこれを避けています。問われるのは「このコントラクトは安全か」ではなく、**「自分は時間内に抜け出せるか」**です。
>
> 💡 **回収可能額で評価するのは、攻撃を移転として記録するためです。**額面で評価すると、参加者Tが自ら価格を決めるオラクルの市場を作り、無価値な担保を高く評価させて他者の資金を借り出しても、貸し手の供給ポジションは額面のまま残ります。すると場全体の資産が増え、**攻撃はスコア上「存在しない」ことになります。**回収可能額で評価すれば、貸し手の減少と借り手の増加が一致し、移転として記録されます。
>
> 💡 評価時点のその瞬間の価格を1点だけで使わないのは、期末に自らプールの価格を動かして時価を膨らませる操作を成立させないためです。中央値方式では、評価を動かすには評価時点前の複数ブロックにわたって価格を維持し続ける必要があり、その間ずっと反対売買に晒されます。

### 4.2 初期資本

すべてのエージェントは、**25,000 USDC** から競技を開始します。これに加えて、トランザクション手数料（ガス）用の ETH（● — 評価設定として公表します）が付与されます。

ベンチマーク（§4.3）にも同一の初期資本とガス用 ETH が付与されます。スコアはベンチマークとの差分で算出されるため（§4.4）、ガス用 ETH の価格変動そのものはスコアに影響しません。

### 4.3 ベンチマーク

各評価グループに、**初期資本を一切動かさず保持する参照エージェント（ベンチマーク）**を1体配置します。ベンチマークは取引を行わず、順位の対象にもなりません。

### 4.4 スコア

### 4.4.1 計算式

各エポックは、一定ブロック数（付録A）ごとの**評価区間**に区切られます。1エポックあたりの区間数を `K`、区間境界 `e` におけるエージェント `a` の資産価値（§4.1）を `V_e` と書きます。**最終スコアは、ライブ競技期間の全エポックを通算したものです。**

```
床処理後の資産価値     W_e = max( V_e , 0.01 × W_0 )        （W_0 はエポック開始時の資産価値）

区間ごとの超過対数リターン
                      x_e = ln( W_e / W_{e-1} ) − ln( B_e / B_{e-1} )     e = 1 … K
                            （B はベンチマークの同じ境界での資産価値）

エポックのスコア       E(a, s) = mean( x_e ) − λ × std( x_e )

最終スコア             Score(a) = ( Σ_s E(a, s) ) / N
```

- `mean` は算術平均、`std` は母集団標準偏差（分母 `K`）です
- `λ`（リスク回避係数）は ●（評価コードの公表時に確定し、凍結します）
- `K` はすべてのエージェントについて同一の値を用います。エージェントの脱落等により系列が短くなっても、分母は短くなりません
- **`N` は、ライブ競技期間において有効と確定したエポックの数（k）**です。§4.4.2 により無効としたエポックは `N` から除外し、**その除外はすべての参加者に一律に適用します**
- 有効エポック数は、最終順位の発表時に公表します
- **すべての有効エポックを等しく重み付けします。**レジームによる重み付けは行いません

> 💡 **エポックごとに環境が初期化される**ため、資産は次のエポックへ引き継がれません。式の意味は2つに分かれます。**平均項** `mean(x_e)` は、途中の項が打ち消し合うため、エポック末の `( ln W_K − ln W_0 ) − ( ln B_K − ln B_0 )` を区間数で割ったものに一致します。つまり「ベンチマークに対して、そのエポックでどれだけ資産を増やしたか」です。**控除項** `− λ × std(x_e)` は「その増やし方がどれだけ荒かったか」の減点です。
>
> 損益額をそのまま合計すると、**1回の大勝ちで他のすべての回の失敗を覆い隠せてしまい、過大なリスクテイクが最適戦略になります。**対数を用いることで破産した回が強く効き、控除項を置くことで、**すべてのエポックで安定して増やした参加者が上位に来ます。**

### 4.4.2 例外的な状態の処理

| 状態 | 処理 |
| --- | --- |
| **資産価値がゼロまたは負** | 床処理により `W = 0.01 × W_0` として扱います。対数が発散することはありません |
| **ベンチマークの資産価値が床を下回る** | ベンチマークにも同じ床処理を適用します |
| **区間境界の資産価値が取得できない** | 直前の値を持ち越し、当該区間の `x_e` を 0 として扱います。取得の失敗は環境側の事象として記録し、参加者の不利益に扱いません |
| **評価に用いる価格の履歴が5ブロックに満たない** | 利用可能なブロックの中央値を用います。履歴が全くない場合は、エポック開始時の参照価格を用います |
| **エージェントがタイムアウトまたは異常終了した** | 当該ブロックは行動なしとして扱います。スコア上の追加のペナルティはありません |
| **§2.3 の再起動上限を超えて凍結された** | **採点上の凍結**として扱います。以後の区間の `x_e` をすべて 0 とします（§4.5） |
| **主催者の設備に起因してエポックが完了しなかった** | 当該エポックを無効とし、同一のシードで再実行します。再実行できない場合、**当該エポックをすべての参加者について `N` から除外します**（一部の参加者についてのみ除外することはありません） |
| **参加者側の事由でエポックが完了しなかった** | **採点上の凍結**として扱います。以後の区間の `x_e` をすべて 0 とします |

### 4.4.3 評価の再現性

- 順位はスコアの降順とします
- **評価に用いるコードのリポジトリ、コミットハッシュおよび設定値（付録Aの各項目を含みます）は、提出期間の開始までに公表し、ライブ競技期間の開始時点で凍結します**
- **各エポックの生成に用いるシードは、提出期間の開始前にそのハッシュ値を公表し、結果発表後に原本を公開します**

**再現できる範囲は、次のとおり異なります。**

|  | 内容 | 誰が行えるか |
| --- | --- | --- |
| **完全な再生** | 参加者成果物（**初期戦略コードおよび各改訂版の戦略コード・版の切替記録**を含む）、シード、評価コードを用いた、意思決定を含む完全な再実行 | **主催者のみ。**参加者成果物は当該参加者の同意なく公開しないため（参加規約 第27条第2項第3号） |
| **自己の評価の検証** | 自己の参加者成果物と、主催者から開示される自己の**戦略コード版・切替記録**・シード・評価コードによる再実行 | **各参加者**（異議申立ての手続において、主催者が必要な記録を開示します） |
| **公開情報による検証** | 公開されたシード、評価コード、加工済みログ、集計値および検証用ハッシュ値による、スコアの算出過程の検証 | **第三者** |

**各エポックのスコアは、当該エポックの終了後にリーダーボードで公開します。**通算スコアも同時に更新します。参加者は、自分のスコアがどのエポックで積み上がったかを追えます。

**第三者による完全な再実行は、参加者成果物が公開されないため行えません。**主催者は、第三者が検証できる範囲を上記の第3行に限って表示します。

### 4.4.4 指標の性質

| 行動 | 帰結 |
| --- | --- |
| 何も取引しない | ベンチマークと同一の資産推移になるため、スコアは 0。正のスコアを出したすべての参加者に負けます |
| 過大なレバレッジで破産する | 当該エポックのスコアが大きな負値となり、1回の破産が数十エポック分の好成績を打ち消し得ます |
| 相場全体が上昇する | ベンチマークも同率で上昇するため、相場つきの運は平均項では相殺されます。ベンチマークから離れた分は `std` に乗り、`λ` により控除されます。方向を当て続けない限り優位にはなりません |
| 安定して複利で資産を増やす | 平均項が大きく変動項が小さいため、最も高く評価されます |

### 4.5 破産と凍結

- 区間境界の資産価値が**エポック開始時の資産価値の1%を下回った**時点で、当該エージェントはそのエポックにおいて**破産**として扱われます
- 破産は**採点上の凍結**です。以後の区間の超過対数リターン `x_e` はすべて 0 として扱われ、その後の損益はスコアに一切反映されません。トランザクションの送信自体が技術的に妨げられるわけではありませんが、それによりスコアが変動することはありません
- 破産は失格ではありません。**スコア上のペナルティは、床処理された資産価値がそのまま計算に算入されることによってのみ生じます。**別途の減点は行いません
    - 破産したエポックの `E(a, s)` は、合計およそ `ln(0.01) ≈ −4.6` の対数損失を区間数で割った平均項に、変動の控除が加わった大きな負値になります
- **有効エポック数 `N` の20%を超えて破産した参加単位は、最終ランキングから除外します。**閾値となるエポック数は `N × 0.2` の小数点以下を切り上げた数とし、**これを超えた場合**に除外します。除外された場合の賞金の取扱いは、参加規約 第20条第2項によります

> 💡 凍結後の区間を 0 として扱うのは、凍結された参加者のスコアがその後のベンチマークの値動きで動かないようにするためです。資産価値を凍結時点で固定するだけだと、ベンチマークが上昇し続ける局面で、凍結後も毎区間 `− ln( B_e / B_{e-1} )` を積み続けてしまいます。

### エポックの無効判定

| 項目 | 内容 |
| --- | --- |
| 無効とする事由 | 主催者の設備、ネットワークまたは評価基盤に起因して、エポックが最後まで実行されなかった場合に限ります |
| 判定する者 | **主催者の運営責任者**が判定し、判定の理由と時刻を記録します |
| 再実行 | **同一のシードで最大2回まで**再実行します。2回とも完了しなかった場合、当該エポックを無効として確定します |
| 適用範囲 | 無効は**すべての参加者について一律に適用**します |
| 有効エポック数が予定の半数を下回った場合 | **主催者は、審査期間（11/9〜11/30）を用いて追加のエポックを実行します。**この場合、追加のシードのハッシュ値をあらかじめ公表します |
| `N = 0` の場合 | 参加規約 第34条により、本大会の中止として取り扱います |

### 4.6 タイブレーク

スコアが同一の場合、次の順に適用します。

1. エポック間のスコアの標準偏差が小さい方
2. 最も成績の悪いエポックにおけるスコアが大きい方
3. 最終提出の時刻が早い方

**上記のすべてによっても順位が定まらない場合、当該参加単位は同着とします。**

同着の場合の賞金は、次の手順により算出します（参加規約 第18条第3項）。

1. 同着者が占めることとなる順位に対応する賞金の**合計額**を求めます
2. これを同着者の数で除し、**1円未満を切り捨てた額**を各同着者に配分します
3. **切り捨てにより生じた残額は、同着者のうち最終提出の時刻が最も早い者に加算します。**最終提出の時刻は、主催者のシステムが提出を受理した時刻によります
4. **次の順位は、同着者の数に応じて繰り下がります**

> 💡 例：2位に3者が同着した場合、2位・3位・4位の賞金の合計（500,000円 + 300,000円 + 200,000円 = 1,000,000円）を3で除し、切り捨てて各者 **333,333円**。残額 **1円**を、最終提出の時刻が最も早い者に加算するため、当該者は **333,334円** となります。次の参加単位は5位です。

### 4.7 リーダーボードの運用

| 期間 | 表示内容 | 最終評価への算入 |
| --- | --- | --- |
| 提出期間（9/23〜10/31） | 試行環境（§2.7）は順位を掲示しません。公開セット35シナリオでの自己評価に用いてください | しません |
| **ライブ競技期間（11/1〜11/7）** | **§4.7.1 の方式で k エポックを実行し、エポックごとにスコアと通算順位を更新します** | **します** |
| 審査期間（11/9〜11/30） | 違反の監査、レポートトラックの審査、順位の確定を行います。新たなエポックは実行しません（§4.5 の例外を除きます） | — |

**最終順位は、ライブ競技期間の k エポックを通算したスコアによって決まります。**

### 4.7.1 ライブ競技の実施方式

**ライブ競技期間中、主催者は、1エポックを1単位として、環境を初期化しながら複数回実行します。**

- **1エポック**：全参加単位が同一の初期条件から開始し、所定のブロック数を実行して終了する単位
- **実行回数**：期間中に **k 回**（k の値は提出期間の開始までに公表します）
- **各エポックの開始時に環境を初期化**します。前のエポックの資産・ポジションは引き継ぎません
- **全参加単位のエージェントは、各エポックにおいて同時に開始します**
- **各エポックの結果はその都度リーダーボードに反映し、通算スコアを更新します。これが最終順位を決めます**
- 各エポックのシナリオは**非公開セット**（§3.3）から生成され、参加者に事前に知らされません

> 💡 ライブ競技を複数回に分けるのは、**単一の実行に結果が左右されることを避けるため**です。エージェントは 10/31 の提出締切で凍結されており、各エポックのシナリオは事前に知らされないため、特定の展開に賭けた偶然の勝利は k 回の通算で薄まります。

## 5. レポートトラック

### 5.1 応募

- **リーダーボードトラックに有効なエージェントを提出した参加単位**が応募できます。最終順位は問いません
- **1参加単位につき1本**
- **締切：2026年11月21日**
- 日本語または英語

### 5.2 レポートに含める内容

1. サマリー（4〜6文）
2. エージェントの設計（アーキテクチャ・戦略・使用モデル）
3. 何が効いたか（最も重要だった工夫と、その検証結果）
4. より単純な代替案との比較（最終成績の大部分を再現できる最小構成はどこまでか）
5. 実行コスト（推論時間・API費用など）
6. 失敗と学び
7. 安全性・市場構造への示唆
8. 再現手順（**実行ログの識別子の引用を含みます**）

### 5.3 審査基準

審査員パネルが、次の5つの基準で採点します。

1. 新規性・独創性
2. 技術的な正確性と深さ
3. 再現性・証拠
4. 明瞭さ
5. コミュニティ・安全性への示唆

**定量的な主張には、競技環境における実行ログの識別子の引用を求めます。**すべての取引ログが保全されているため、主催者はレポートの主張を客観的に検証します。

### 5.4 部門

レポートは、次の3部門のいずれかを選んで応募します。

| 部門 | 対象 |
| --- | --- |
| **Trader** | 市場価格や流動性を分析し、売買、裁定、流動性提供を通じて収益の獲得を目指す設計 |
| **Hacker** | 市場、スマートコントラクトまたは他のエージェントの判断に存在する弱点を探索し、経済的な攻撃を試みる設計 |
| **Verifier** | スマートコントラクトや市場の挙動を分析し、脆弱性や攻撃の兆候を検出する設計 |

## 6. 賞金

### 6.1 リーダーボードトラック（金3,000,000円）

| 順位 | 賞金 |
| --- | --- |
| 1位 | 1,000,000円 |
| 2位 | 500,000円 |
| 3位 | 300,000円 |
| 4位 | 200,000円 |
| 5位 | 150,000円 |
| 6位〜15位 | 順に 130,000円 / 120,000円 / 110,000円 / 100,000円 / 90,000円 / 80,000円 / 70,000円 / 60,000円 / 50,000円 / 40,000円 |

- 同着の場合の取扱いは §4.6 によります
- **6位以下の入賞は、最終スコアが 0 を上回ること（ベンチマークを上回ること）を条件とします**
- 失格、辞退または受賞手続が行われなかった場合は、次点の参加単位が繰り上がります
- **繰り上げによってもなお受領者が定まらない部分、および前記の条件を満たす参加単位が所定の数に満たない場合は、参加規約 第20条第2項第1号により、第1位から順に当初の配分額に比例して加算します**

## 8. 禁止行為

禁止行為および違反に対する措置は、**参加規約 第14条から第16条**によります。

競技環境内において、他の参加者のエージェント、スマートコントラクトまたは市場構造の弱点を突く行為は**競技の一部として認められます**。**自らのスマートコントラクトを配置すること、およびそれが他の参加者にとって不利に働く設計であることも、認められます**（§3.1）。一方、次の行為は**禁止されます**。

- 競技基盤そのものへの攻撃、および実行環境の隔離の回避
- **ブロックの処理能力の占有**（§2.6 のガス上限を超えるトランザクション、および1ブロックあたりのガス上限を超える送信）。他の参加者だけでなく**環境の参照価格更新**を締め出す行為であり、対戦相手に対する行為ではなく競技基盤に対する行為として扱います
- **環境が保有するコントラクトおよびウォレットへの干渉。**次は「他の参加者のもの」ではありません: 参照価格コントラクト（PriceFeed）、レジストリ（MarketRegistry）、環境が配置した各 venue とそのオラクル、フロー用ウォレット、および運営の資金ウォレット。**これらに対する特権操作を発見した場合は、実行せず主催者に報告してください**（レポートトラックの対象になります）
- **競技環境の状態を直接操作する機能（残高・価格・チェーン状態の書換え等、環境の運用にのみ用いられる API）の呼び出し**
- 主催者の設備・運営基盤そのものへの攻撃、外部ネットワークへの影響、および他の参加者の環境への干渉
- 人為的介入（提出凍結後にエージェントの挙動を外部から変更する行為）
- チーム間の共謀、および複数チームへの参加
- 自己取引による利益移転（同一参加単位または共謀関係にある複数エージェント間で、市場を介して意図的に資産を移す行為）
- 評価価格の操作（評価時点の価格を歪めることを目的とする取引。§4.1 の中央値方式で緩和されますが、検出された場合は違反として扱います）
- 非公開シナリオの探索（非公開セットのシードや発生スケジュールを特定しようとする行為）

いずれも、§7 の保全された記録に対する事後の監査により検出します。
