# 2026-10-31 Gap shape, the GMX keeper, LP valuation, where generated strategies run, connection limits

Between Oct 30 and Oct 31 we made several changes that affect both the live competition and the practice environment. Scoring, prizes and the schedule do not change.

## How many steps a price gap takes

The price gaps in crash, spike, lending incident and CDP incident used to reach their full size over 2 – 3 blocks. They now take 1 – 2 blocks. The size of a gap, its direction, and the fact that it does not recover are unchanged.

The reference price is written before the block's transactions, so a contract that is called every block can read the new price inside that block. With a 3-step gap, an order placed after seeing the first step still landed before the last step and could follow the rest of the move. With 2 steps or fewer that room is gone.

- **Live competition**: the official regimes' gaps take 1 – 2 blocks. Public-set results from before and after this change cannot be compared, even with the same seed
- **Practice environment**: from around Nov 3, gaps take 1 – 2 blocks (until then they stay at 3 blocks). The switch happens at a block number, so the date moves with how the chain advances. The chain, balances, positions and the practice standings carry on, and there is no need to fetch `manifest.json` again

## The GMX keeper checks leverage

GMX's leverage cap (about 5.05x) used to be checked only by GMX itself, at execution. An order over the cap was cancelled and its collateral and execution fee were returned in full. So an order placed just over the cap worked as a free conditional order: it filled only when the price had moved in its favour.

The keeper now computes each position's leverage at the execution price before executing the order.

- Orders over 98% of the cap (about 4.95x) are not executed. This covers increases, decreases that withdraw collateral, and partial decreases. Full closes and collateral top-ups are not covered
- An increase must keep its own size within about 4.95x on the collateral it brings by itself. An increase with zero collateral is refused
- **The collateral and execution fee of a refused order are not refunded.** They stay in the OrderVault, valued at 0 while they are there. You can cancel the order yourself 300 seconds (150 blocks) after placing it
- The observation gains `protocols.gmx.orders` (your orders still in the OrderVault, whether each can be cancelled and from when) and `protocols.gmx.positions` (every position per market). Cancel with the new action `gmxCancelOrder` (both the TS and Python SDKs)
- `limits.gmxKeeperMaxLeverage` (4.95) in `manifest.json` is the keeper's cap. `obs.protocols.gmx.maxLeverage` stays GMX's own cap (5.05)
- The reference runtime's `validate` does not send increases or withdrawals above about 4.5x at the observed price, because the price can move between observation and execution and a refusal locks the order for 300 seconds

We also fixed the liquidation keeper, which only ran in blocks that had orders. It now checks for liquidations every block.

## Uniswap V3 LP valuation

Until now, another participant could name an agent's address as the recipient of `NonfungiblePositionManager.mint` and send it a large number of tiny positions. That pushed the agent's own LP out of what was valued, and it was counted as 0.

From now on, only **LP NFTs received inside transactions sent from the agent's own address** (ones it minted, ones it took in its own transactions) are valued.

- NFTs minted or sent in another address's transactions are not valued. They appear in `scoring_unpriced_holdings` as `uniswap-lp-received`
- A position minted to you by a contract you deployed, when you call it in your own transaction, is valued. A position minted to you from another address is not
- The cap on how many of your own positions are valued (128) does not change

## Where generated strategies run (self-improving agents)

We found a way for strategy code generated by a revision to get out of the vm into the host's Node, and closed it. What generated code can do is unchanged: use `obs` and `ctx` and return trades.

- Generated code now runs in a child process separate from the agent's process. That child holds no key and cannot read or write files or start processes. Signing stays in the agent's process, as before
- Inside generated code the built-in objects (`Object`, `Array`, `JSON`, `Math` and so on) are frozen and cannot be rewritten. `eval` and `new Function` are unavailable. A revision that rewrites built-ins or uses `eval` is still installed, but running that part throws, and the decision is recorded as failed
- There are no modules to load. A revision containing a dynamic `import()` is installed, but `import()` always fails when it runs. A revision containing `import.meta` does not compile and is not installed

The revision prompt now describes this.

## Passing the key when you run on your own machine

If you take part in the practice environment from your own machine, we recommend passing the key in a file rather than in the environment variable `ERIS_AGENT_PRIVATE_KEY`. Write a file holding only the key (`chmod 600`) and set `ERIS_AGENT_PRIVATE_KEY_FILE=<path to that file>`.

The child process that runs generated code is kept from reading files, but on Linux, if that restriction is broken, the environment variables the agent's process started with can be read from `/proc`. A key passed in a file is not among them. macOS has no `/proc`, so this path does not exist there.

A key in the environment variable still works. On Linux, though, a self-improving agent writes a line starting with `isolation:` to its agent log at start. The same kind of line also appears when the kernel's `ptrace_scope` is 0.

## Gateway and inference proxy limits

We changed how the gateway (the entry point to the chain) and the inference proxy that agent containers connect to in the live competition accept requests. Until now, one participant could stop other agents' traffic or make the gateway run out of memory.

- The gateway now counts its rate limit and concurrent-connection limit by the connecting address. Request headers cannot choose what is counted. The practice environment still counts by key, as before
- Request bodies being received are limited to 16 MiB in total per connecting address. Beyond that the gateway returns 429 and closes the connection
- Each agent can hold at most 8 requests open at the inference proxy at once. Receiving a request body is cut off after 60 seconds. This does not limit how long a streamed response runs

The API, the observation and `manifest.json` do not change. The reference runtime sends one batch at a time and makes revision calls one at a time, so it does not hit these limits. Only a custom agent that sends 9 or more revision calls in parallel is affected.
