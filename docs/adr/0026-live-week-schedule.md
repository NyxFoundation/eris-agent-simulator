# ADR 0026: ライブ競技週の編成 — k = 60・1 エポック 360 ブロック・ガス用 ETH 3・時刻表どおりの実行

## Status

Proposed（2026-09-27）。**運営が確定させる値**は §1〜§4 の 4 つ（k = 60 が commit 済みの非公開セットで成立するか、
360 ブロック、3 ETH、週への均等配置）。確定したら規約付録 A に公表する（ascon-web 側の別 PR）。

**実装済み（同日、この ADR と同じ PR）**: `npm run backtest -- --scenarios <plan> --follow-schedule`（各エポックの
`startsAt` まで待ってから始める。`core/src/backtest/timetable.ts`）と `npm run competition -- plan … --ends-at <ISO>`
（k 本を窓に均等配置する。`spreadOver` in `core/src/competition/schedule.ts`）。**未実施**: 公式レジーム 12 本の
`funding.ethWei` を 3 ETH にする変更（本 PR はレジーム YAML を触らない。§3）。

## Context

**規約が公表を約束している値がどこにも無い。**規約（ascon-web `content/legal/rules.md`、2026-09-22 発効）は
k（§4.4.1・§4.7.1）、1 エポックあたりのブロック数（§2.5・§4.7.1）、ガス用 ETH（§4.2）を付録 A の評価設定値とし、
**提出期間の開始（9/23）までに公表する**（§7.1）としている。§2.5 は参加者の推論費用の目安を
`呼び出し回数 ≒ k × 1 エポックのブロック数 ÷ reviseEveryBlocks` と書いているので、参加者はこの 2 つが無いと
費用の上限を決められない。9/27 時点でどちらの repo にも値は無く、公表は既に遅れている。

**旧推奨の k = 40 はコードが拒否する。**`deriveSchedule`（`core/src/competition/schedule.ts`）は k を非公開セットの
レジーム数の倍数に要求し、各レジームから k / R 本を抽選 seed で選ぶ（規約 §3.3「各レジームの出現回数は等しく」）。
ADR 0023 の未決欄にあった「推奨 40 = 8 レジーム × 5」は公式レジームが 8 本だった頃の数字で、今は 12 本
（`config/scenarios/public.yaml`: `spike` #105 / `depeg-persist` #106 / `cdp-incident` #107 / `launch` #29 が加わった）なので
`k = 40 is not a multiple of the 12 regimes` で落ちる。規約本文の「8 レジーム」（§3.3 の表）と「公開セット 40 シナリオ」
（§4.7）も同じ理由で古い（ascon-web 側で直す）。

**実測: 1 エポックは 12 分のブロック時間 + 1〜5 分。**360 ブロック × 2 秒 = 12 分に、setup（デプロイ済み state の
snapshot/revert・資金配布・agent 起動と readiness 待ち）と採点再構成が乗る。ラップトップで 1 エポック 13〜17 分、
c7i.4xlarge で 1 シナリオ ~12.5 分（`config/scenarios/public.yaml` の記録は 795 秒）。**60 エポックはブロック時間で
12 時間**、ライブ競技期間（11/1〜11/7 JST = 168 時間）の 7%。運営の要望は「週を通して競技が動いている」ことで、
12 時間ではない。

**時刻表は打てるが、runner がそれを待たなかった。**`competition plan --starts-at <ISO> --every-minutes <N>` は各エポックに
`startsAt` を付け、backtest runner はそれを `matrix.json` の `schedule` に写し、dashboard が「次のエポック開始予定」を出す。
しかし runner 自身はエポックを連続で回していた。60 エポックの時刻表を週に広げても、1 プロセスで起動すれば最初の
半日で 60 本とも走り、dashboard の「次」は残り 6 日間ずっと過去を指す。時刻どおりに走らせるには、運営が毎回手で
`--resume` を叩くしかなかった。

**ガス用 ETH は今 100 ETH で、P を支配している。**公式レジームは `economicGas: false` で `funding.ethWei` を書いておらず、
sdk の既定（`sdk/src/config.ts`: economicGas が false なら 100 ETH）がそのまま配られる。§4.2 によりガス用 ETH の残高は
資産価値に算入され、時価で P に入る。100 ETH は $3,000 で $300k、採点対象の初期資本（8 WETH + 0.4 WBTC + 25,000 USDC
≈ $73k）の 4 倍。PR #145 の backtest（crash、公開 seed 5 本）では noop の P が +31,368 / −23,002 / +4,887 / +30,324 /
+24,970 で、venue-arb の net PnL（最終価格マーク）+1.6k〜+2.6k を桁で上回った。全員が同じ ETH を持つ限り T では相殺
するが、ネイティブ ETH の量が変わる agent（ガスを多く使う・ETH を他資産に替える）だけ β がずれる。一方、実測の
ガス消費は 1 agent・1 エポックあたり **0.005 ETH 以下**。

## Decision

### 1. k = 60（12 レジーム × 5）

- 各レジーム 5 回。重みは `w_s = 1 + 0.5 (s − 1) / 59`（最初 1、最後 1.5）
- **前提: commit 済みの非公開セットが各レジーム 5 本以上の seed を持つこと。運営が commit 済みのファイルで確認する。**
  確認は `npm run competition -- plan --hidden <commit 済みの hidden set> --lottery <任意の lottery> --k 60` が通るか
  どうか（足りなければ `regime <r> has <n> hidden seed(s) but needs 5 for k = 60` で落ちる。レジーム名が 12 本と
  食い違っても同じく落ちる）。任意の lottery での試行は順序を明かさない（順序は本物の抽選 seed が決める）
- 余る seed は抽選が捨てる（`deriveSchedule` は各レジーム k / R 本をシャッフルして先頭から取る）ので、6 本以上ある
  セットもそのまま使える
- 推論の呼び出し回数の目安（§2.5）は `60 × 360 ÷ 60 = 360` 回 / agent（`reviseEveryBlocks` 既定 60 のとき）

### 2. 1 エポック 360 ブロック（2 秒ブロック = 12 分）

- 公式レジーム 12 本の `run.blocks: 360` のまま。全レジームの較正（台形の長さ・窓の本数・flow wallet の在庫・
  `markMedianBlocks: 5`）はこの長さで測ってあり、参加者が 9/23 から調整している公開セットもこの長さ
- 付録 A の残りの値のうち評価区間は 12 ブロック（sdk 既定。1 エポック 29 区間）で、本 ADR は動かさない

### 3. ガス用 ETH 3 ETH / agent（ベンチマークも同額）

- 実測消費（≤ 0.005 ETH / agent・エポック）の 600 倍。ADR 0011 の economic-gas 既定と同じ値
- ETH 建てのエクスポージャは 108 ETH（100 + 8 WETH）から 11 ETH（3 + 8）になり、ガス用 ETH が P を支配しなくなる。
  ベンチマークにも同額を配る（§4.3「同一の初期資本とガス用 ETH」）ので相殺の構造は変わらない
- **実施は公式レジーム 12 本の `funding.ethWei: "3000000000000000000"`**。本 PR はレジーム YAML を触らない
  （PR #145 はこの判断を「要決定」として残してマージされた）。変えると過去の matrix の P とは比較できない
  （全員に共通の ETH の β が 1/33 になる）
- `economicGas` は false のまま（ガスを経済コストにするかは別の判断。ADR 0011）

### 4. エポックを週に均等に広げ、runner が時刻表どおりに走らせる

```bash
npm run competition -- plan --hidden <hidden.yaml> --lottery <lottery.yaml> --k 60 \
  --starts-at 2026-11-01T00:00:00+09:00 --ends-at 2026-11-08T00:00:00+09:00 --out plan.yaml
npm run backtest -- --scenarios plan.yaml --agents <field.yaml> --follow-schedule
```

- `--ends-at` は窓を k 等分し、各エポックを枠の先頭に置く（`spreadOver`）。168 時間 ÷ 60 = **168 分おき**、最後の
  エポックは 11/7 21:12 JST に始まり、他と同じ 168 分の枠で終わる。開始時刻は運営が決める（11/1 00:00 JST は例）
- `--follow-schedule` は各エポックの `startsAt` まで待つ。**過ぎていれば待たずに即開始し、何分遅れかを出す**。
  遅れは後ろへ波及させない（後続はそれぞれ自分の時刻を待つ）。時刻表の無いプラン・`startsAt` の欠けたエポック・
  リスト順と時刻順の食い違いは anvil 起動前に拒否する
- **`--resume` と合成する。**完了済みエポックは時計を見る前に飛ばすので、再起動すると取りこぼしと失敗分を即座に走らせ、
  それから次の時刻を待つ。1 枠は 168 分でエポックは 13〜17 分なので、枠の残り ~150 分の中で §4.4.2 の再実行ができる
  （待機中のプロセスを止めて `--resume` で起こし直す）。`--agent-state-root` の復元点も従来どおり
- 待機中の anvil は採掘しない（run の teardown が interval mining を 0 にする）。時刻表はコミットメントの外で、採点にも入らない

### 5. 週全体を「動いている」ようにする選択肢

§1〜§4 だけでは、agent が動いているのは週の 7%（ブロック時間 12 時間、wall で 13〜17 時間）。埋める方法は 3 つある。

**(A) エポックを伸ばす。**k = 60 のまま 168 分の枠を埋めるには 1 エポック ~4,500〜4,800 ブロック（今の 13 倍）。要るもの:

1. **公式レジーム 12 本の再較正**。台形（`rampBlocks` / `holdBlocks` / `decayBlocks`）と `minGapBlocks` は絶対ブロック数、
   `windowFrac` は run 長に対する割合、`count` はエポックあたりの本数（#145）。同じ YAML のまま伸ばすと、同じ本数・
   同じ長さのショックが 13 倍の平穏の中に置かれ、全レジームが calm に寄る。whale の本数・launch の波（ramp 20 ブロック）・
   vuln のプール出現・victim の配置も同じ。受け入れ（12 レジーム × 5 seed で「レジームが発火する」、#79）もやり直し
2. **flow wallet の在庫**。1 回配りで 360 ブロック分に合わせてある（`test/flowTrendInventory.test.ts` が各レジームの
   最悪の片寄りから必要在庫を導出して固定している）。導出し直すか `flow.topUpEveryBlocks`（練習は 300、公式は 0）を入れる。
   練習期間の実測では 1 財布の在庫が 1 日に元の数倍揺れた
3. **LST の経済クロック**。`lst.simulatedSecondsPerBlock` 既定 1 時間 / ブロックでは 4,800 ブロック = 200 日分の利回りに
   なる（練習期間は原資 50 WETH が 3.3 日で尽きて 30 秒 / ブロックに下げた）
4. **anvil の履歴深度**（~1,000 ブロック、`reconstruct.ts`）。P は境界でその場に読む（`liveScoring.ts`）ので採点は残るが、
   事後 sweep の equity curve / alpha / market.json は欠ける。state の一時ファイル（macOS の anvil 1.7.1 で 360 ブロック
   1 本 2〜7 GB、Linux 1.8.1 は 0）は 13 倍になるので `--prune-history` が要る
5. **参加者の推論費用が 13 倍**（`60 × 4,800 ÷ 60 = 4,800` 回 / agent）
6. **参加者が 9/23 から調整している公開セットと別物になる**（エポック長は付録 A の値そのもの）
7. 無効エポックの再実行が 1 本 ~2.7 時間（予備日 11/8 に入るのは ~8 本）

**(B) 360 ブロックのままエポックを増やす（k = 12m）。**枠 = 10,080 分 ÷ k が 1 エポックの wall 時間 W を上回る必要がある。
余裕 20% を取ると `k = 12 × ⌊8,064 ÷ (12 W)⌋`。W = 17 分なら m = 39・**k = 468**・枠 21.5 分・ブロック時間 93.6 時間
（週の 56%）。W = 25 分なら k = 312・枠 32 分・37%。要るもの:

1. **各レジーム m 本以上の非公開 seed**。commit 済みのセットが 5 本なら、新しいセットと新しい commit が要る。§7.1 の期限
   （9/23）は過ぎているので、差し替えの告知と新しいハッシュの公表が要る（結果発表後は両方を公開する）。commit 済みの
   セットが既に m 本以上持っていれば、変わるのは k だけ
2. **再較正は要らない**。どのエポックも公開セットと同じ 360 ブロックのレジーム
3. **参加者の推論費用が m / 5 倍**（k = 468 なら `468 × 360 ÷ 60 = 2,808` 回 / agent）。§2.5 の式で予算を立てるので k と
   一緒に公表する
4. **運営側の負荷**: setup（agent 起動・readiness 待ち ≤ 60 秒）と採点再構成を k 回払う。runs/ の成果物が m / 5 倍、
   matrix.json は k × 参加数のレコード（k = 468・500 体で 23.4 万）。週に余りが無いので再実行は予備日へ
   （24 時間 ÷ W ≈ 85 本）。dashboard の「Score by epoch」を k = 468 で描いたことはない
5. **順位の信頼性が上がる**。同一コードの 2 体（違いは tx の着順だけ）の T が 1 エポックで whale#101 は 9.24 点、
   crash / calm / depeg-persist の #101 で 1.1〜2.2 点ずれた（issue #118 D）。Score のこのぶれは 1/√k で縮み、
   k = 60 → 468 で 1/2.8

**(C) k = 60 × 360 のまま、隙間を採点外の展示で埋める。**凍結済みの提出物を練習 devnet の仕組み（ADR 0021）で週の間
走らせ続ける。採点は §1〜§4 のまま。要るもの: 2 台目の box、練習 config（victim・vuln・`persist` が無い = 公式とは別の世界）、
dashboard の `practice` バッジ。**`ERIS_AGENT_FROZEN` で走らせる**（§2.5 は参加者の認証情報を競技の実行にのみ使うとして
いるので、展示で推論を呼ばない）。観戦者が展示と採点エポックを取り違えるリスクが残る。

**推奨: 週を通して動かすことが要件なら (B)。(A) は採らない。**(B) は設定だけで済み（非公開 seed・k・プラン。コードは
本 PR の `--ends-at` と `--follow-schedule` のまま）、どのエポックも参加者が調整してきたレジームと同一で、順位の信頼性まで
上がる。(A) は全 12 レジームと flow / LST / anvil の再較正で、11/1 までの残り 5 週間で受け入れまでやり直すことになり、
しかも参加者が準備した競技を変える。**決めるのは k の公表前**: k は重み `w_s` と参加者の推論予算を決めるので、公表後に
変えると規約の変更になる。(B) を採るなら m は live 規模で測った W から決める（500 体の負荷試験は未実施 = ADR 0023 の未決）。
要件が「観戦できる時間を増やしたい」程度なら §1〜§4 のまま公表し、(C) を任意で足す。

## Consequences

- **dashboard の「次のエポック開始予定」が本当になる**。runner が時刻表どおりに走るので、`matrix.json` の `schedule` が
  過去を指し続けることはない。遅れたエポックは runner のログ（`s=N …: planned for …, starting now, 12m 05s late`）に残る。
  時刻表を詰め直す機能は無い（遅れは後続に波及させない）
- **エポック間で anvil が 2.5 時間待つ**。採掘は止まっている（teardown が interval mining を 0 にする）。次のエポックは
  snapshot に revert して始まるので state は同じだが、最初のブロックの timestamp は待った分だけ進む。state dump の年齢
  （数日）で既に同じことが起きているので新しい種類のずれではないが、2.5 時間の待機を挟んだ実走はまだない。
  **本番前に短い時刻表（例 `--every-minutes 30` で 3 本）で 1 回通す**
- **matrix.json は最初のエポックが終わるまで書かれない**。11/1 より前にプロセスを起動しておくと、それまで dashboard は
  この competition を出さない（「開始予定」を週の前から出したいなら別途）
- **state の一時ファイル**: macOS の anvil 1.7.1 は 360 ブロック 1 本で 2〜7 GB を `~/.foundry/anvil/tmp/` に残す
  （CLAUDE.md の 2 回の実測）。1 プロセスで 60 本なら 130〜420 GB。本番 box の anvil が書かないこと（Linux 1.8.1 では 0
  だった）を確かめるか、backtest anvil に `--prune-history <N>` を付ける。N はエポックの事後 sweep が読む窓より大きく
  する（練習チェーンの 300 では 360 ブロックの sweep が履歴の外に出る）
- **規約側の修正**（ascon-web の別 PR）: 付録 A の k・エポック長・ガス用 ETH・評価区間、§3.3 の「8 レジーム」、§4.7 の
  「公開セット 40 シナリオ」（今は 12 × 5 = 60）
- **ADR 0023 の未決欄の「推奨 40」は本 ADR が置き換える**
