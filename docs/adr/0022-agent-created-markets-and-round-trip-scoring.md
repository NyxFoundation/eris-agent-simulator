# ADR 0022: エージェントが作る市場と、ラウンドトリップ採点

## Status

Accepted（2026-09-05）。issue #40 の実装。ADR 0014（環境が仕掛ける vuln プール）が
「後で決める」と明示していた honeypot トークン / owner drain / 偽オラクル / proxy 難読化を、
**環境ではなくエージェントが仕掛ける側に置き換える**決定。

## Context

これまでエージェントが触れる venue は**環境がデプロイしたものだけ**だった。したがって
「流動性はどこに置かれるべきか」「そもそもどんな市場が存在すべきか」「このコントラクトは
触って安全か」は、どれも競技が報酬を与える判断ではなかった。

一方で規約は反対側をすでに認めている。§8 は**他の参加者のエージェント・コントラクト・
市場構造の弱点を突く行為を競技の一部**として認めており、レポートトラックには Hacker と
Verifier の部門がある。にもかかわらず、Hacker が仕掛ける相手も Verifier が検証する対象も、
環境自身の `vuln` レジーム以外には存在しなかった。

ADR 0014 は環境側の半分を作った（rigged プール、factory ログによる発見、事前の dry-run +
codehash + LLM 監査、`discovery-arb` / `discovery-arb-verify` の対）。**デプロイする主体を
環境からエージェントへ移す**と、ADR 0014 が寄りかかっていた 3 つが同時に消える:

1. **ground truth** — 環境はどのコントラクトが仕掛けかを知らなくなる
2. **権威ある開示** — 環境が書いた disclosure が存在しなくなる
3. **評価** — 環境は未知のコントラクトの価格を知らない

## Decision

### 1. ラウンドトリップ公理（3 つ）

3 つ全部を一度に置き換えるのが**ラウンドトリップ規則**である。

1. **環境が評価できないコントラクトの中に残った価値は、エポック最終ブロックで 0。**
   ただし、そのコントラクトを**通り抜けた**利益は満額数える。ブロック 100 で 10,000 USDC を
   預け、ブロック 500 に 11,000 引き出し、エポックが 600 で終わるなら +1,000 は計上される。
   計上されないのは、鐘が鳴った時点でまだ中にあるものだけ。
2. **エージェントが発行したトークンは、発行者にも保有者にも 0。**
   LP ポジションはプールの**既知**リザーブに対する持分で評価する。
3. **verified な venue のポジションも、par ではなく回収可能額でマークする。**

それぞれの理由:

- **(1) は未知コントラクトを評価する必要そのものを消す** — シミュレーションも ground truth も
  偽造面も要らない — **しかも関わる誘因を保ったまま**。ここが前案（claim-based scoring）を
  殺した論点でもある。未知の保有を常に 0 にすると「検証されていないものには一切触らない」が
  完全かつ支配的で思考不要の戦略になり、罠は一度も発火せず Verifier は何も判断しなくなる。
  ラウンドトリップ規則の下では最適手が「**自分は抜け出せるか**」の判断になり、それはまさに
  Verifier の技能である。そして**あらゆる罠クラスが単一の失敗様式に潰れる: 時間内に
  抜け出せなかった**。honeypot も、売れないトークンも、proxy 差し替えも、owner drain も、
  全部これ 1 つ。
- **(2) は帳簿を合わせるため。** 回収可能額でマークすると、1,000 USDC を持つプールは
  トークン保有者に ~1,000 を、LP 保有者にも同じ 1,000 の持分を計上してしまう。
  最終時 0 なら、プールの USDC はちょうど 1 回、LP を持つ者にだけ計上される。
- **(3) は選択肢ではない。** 実例: T が `(loanToken=USDC, collateral=SCAM, oracle=T 自身,
  lltv=90%)` を作る。V が 10,000 USDC を供給。T は無価値な SCAM を差し入れ、自分のオラクルで
  高くマークし、10,000 を借りて EOA へ引き出す。**par なら** V の供給ポジションは依然 10,000 と
  読め、V は何も失っておらず T は +10,000、場の総和が 10,000 増える。これは捏造された価値で、
  攻撃はスコア上「存在しない」。**回収可能額なら** V は −10,000、T は +10,000 の移転になる。

帰結を一言で言うと: **未知のコントラクトは鐘をまたいで価値を保存できない。**
継続的な市場運営は verified な kind の中で可能で、任意バイトコードは
ラウンドトリップ専用の道具である。

### 2. 実装上の帰属（誰がどの数字を持つか）

| 数字 | 持ち主 | なぜそこか |
|---|---|---|
| 未知コントラクトに残した既知トークン | `sdk/src/agentMarkets.ts` の `StrandedLedger` | Transfer ログの**ネット**。残高ではない（プールの 1,000 USDC は LP 保有者のものなので、預けた側にも計上すると二重になる） |
| 貸出ポジションの回収可能額 | `sdk/src/protocols/lending.ts` の `backedFraction` | idle な loan token ＋ **環境価格**で見た担保。市場自身のオラクルは清算だけを決め、マークは一切書かない |
| 借り手のポジション | 同上、`max(0, 担保 − 債務)` | 担保が債務より安ければ担保を捨てて歩き去れる。Liquity アダプタが ICR<100% の Trove に対して既に適用している規則と同じ |
| ガス予算違反 | `core/src/postRunCheck.ts` の `checkGasViolations` | receipt 由来の `gasUsed`（blocks.csv 最終列）。自己申告ではない |

**未知コントラクトの評価は「変えた」のではなく「報告するようにした」**という点が重要である。
EOA の掃引はもともとそこを見ておらず、どのアダプタも請求しないので、値は元から 0 だった。
0 のままにすると「未知コントラクトに 10,000 置き忘れた」と「取引で 10,000 溶かした」が
`summary.json` 上で見分けられない。だから `scoring_unpriced_holdings` に
`reason: "unrealizable"` で出す。

### 3. 発見は環境側・ログ優先。取りこぼしは受け入れる

`contracts/MarketRegistry.sol` は **PriceFeed パターンの 2 例目**。admin ウォレットからの
owner-gated write、1 エントリ 1 イベント、`count()` / `all()` / `isRegistered()`。
1 ブロックの配布遅延をそのまま継承するので、**作った本人は他の誰よりも 1 ブロック早く
自分のコントラクトを知っている** — この head start が作る誘因である。

発見経路は Uniswap V3 `PoolCreated`、貸出シングルトンの `CreateMarket`、そして各ブロックの
トランザクションを `to === null` で走査する top-level CREATE スキャン。**コントラクト内部からの
CREATE / CREATE2 は取りこぼす。** これは受け入れる: 取りこぼしは対称で、
**誰にも見えないコントラクトは誰も釣れない。**

- **codehash は登録時のものだけを記録し、更新しない。** ラウンドトリップ規則の下では、
  観測と執行の間に差し替えられた proxy は「抜け出せなかった」の一形態でしかないので、
  環境が取り締まる必要がない。`eth_getCode` は誰でも呼べるので、気づくかどうかが技能差になる。
- **登録はブロックあたり上限つき・環境負担。** デプロイ自体はエージェントのガス（ADR 0011）だが
  registry への write は環境が払うので、上限がないと deploy-spam が環境コストを無限に膨らませる。
  あふれた分は次ブロックへ繰り越し、factory 由来の kind を先に出す。
- **registrar のアドレスは run 内の誰のものでもない**ことを起動時に検査する（主張ではなく検査）。
  理由が 2 つあり、重いのは 2 つ目である:
  (a) **nonce** — oracle 更新は毎ブロック admin から送られており、同じ鍵に 2 送信者がいると
  奪い合う（LST の償還レートが 1 run 凍った事故と同じ形）。
  (b) **権限** — `MarketRegistry` の owner は deploy した者で、owner だけが登録できる。
  参加者がその鍵を持っていたら、**自分の罠を `verified` として publish できてしまう** —
  環境がコントラクトについて行う唯一の主張を、その主張が守るはずの相手が行うことになる。
  比較は鍵ではなく**アドレス**で行う（ADR 0021 §2 の external 参加者は鍵を運営が持たないため）。

### 4. 貸出は verified な kind として第一級

Aave の reserve は `PoolConfigurator` が開き、それは `POOL_ADMIN` しか呼べない。
つまり **admin を渡さずに Aave をエージェントへ開くことはできない**ので Aave は環境専用のまま。
代わりに `SimpleAMM.sol` の精神で自前のシングルトン `contracts/SimpleLending.sol` を置く。
市場は `(loanToken, collateralToken, oracle, irm, lltv)` で、`createMarket` は誰でも呼べる。
**検証者が codehash 照合できる、環境所有の正典コード**であることが目的で、
本番プロトコルの vendoring が目的ではない。

- **オラクルは任意アドレス。作成者が握っていてよい。** ADR 0014 が先送りした偽オラクルクラスを、
  普通の市場パラメータとして実現したもの。Verifier の仕事はオラクルのアドレスを読んで
  **誰が動かせるか**を問うこと。
- **金利は実時間で積むので装飾である。** エポックは 360 ブロック × 2 秒 = **12 分**、
  3%/年は 12 分で 0.00007%。この長さでは利回りは誰も釣れない。効く餌は即効性のあるもの —
  **見かけ上有利なレート・レバレッジ（高 LLTV）・清算ボーナス** — なので、貸出の罠の被害者は
  **借り手か清算人**であって供給側ではない。IRM は正直に「装飾」と書いた上で同梱する。
- **不良債権は供給者に着地する**（Morpho Blue と同じ社会化）。公理 (3) が実装可能なのは
  この性質のおかげである。

### 4.5. 回収可能額は全 venue の規則である（Amendment 1、2026-09-05）

**当初この ADR は公理 3 を新 venue にだけ適用し、既存 venue（Aave / LST / Liquity）への統一を
「決めていないこと」に置いた。**理由は「既存 venue では回収可能額 ≈ par なので数字が動かない」
「LST の par / realizable は ADR 0019 §3 との関係で未決」だった。**両方とも、やらない理由には
なっていなかった。**

- 「数字が動かない」は**統一しない理由ではなく、統一が安全である理由**である。動かないなら
  過去 run との比較可能性も壊れない
- LST が未決だったのは「どちらが正しいか分からない」からではなく、**決める場が無かった**から
  である。公理 3 がその場を作った: 額面で評価すると攻撃が捏造された価値として記録される、
  という議論は LST venue にも CDP にもそのまま通る

したがって**採点系列は全 venue で回収可能額を取る**（`reconstruct.ts` が
`liquidatableValueUsdc` を合計する）。同じ経済状況を置き場所によって別の点数にしないことが
目的で、具体的には次の 3 つが 1 つの規則に潰れる:

| これまで | いま |
|---|---|
| 出金キューに残ったまま鐘を迎えた LST 償還 → par で採点、差は診断値 | 実際に得られる額で採点 |
| ICR<100% の Trove → Liquity アダプタが 0 で clamp（venue 固有の扱い） | 同じ規則の一例 |
| 水面下の Aave 建玉 → 負の値で採点 | **変えない**（下記） |

**Aave の借り手には床を入れない。**一度入れて、レビューで戻した。

床（`max(0, 担保 − 債務)`）は**対になって初めて正しい**。「借り手は借りた資産を持ったまま、債務より
安い担保を捨てて去れる」と言うなら、その差額を**誰かが被る**という反対側が要る。Liquity では
Stability Pool が吸収し、`SimpleLending` は不良債権を供給者へ社会化するので、どちらもアダプタが
反対側の損失を見ており、帳簿が閉じる。

**Aave にはその機構が無く、このアダプタもモデル化していない**（aToken は何が起きても 1:1）。
借り手だけ床を入れると、場の総和が不足分だけ増える —— **公理 3 が防ごうとしているものと同じ現象に、
反対方向から到達する**。よって Aave は `担保 − 債務` のまま（水面下では負）で、それは
ウォレット側の借入資産をちょうど相殺する。

残るのは「**Aave の不良債権をモデル化していない**」という既知の制約で、隠さず書く。閉じるには
供給側を裏付け不足のぶんだけ切り下げる必要があり、それには `getUserAccountData` が持たない
reserve 単位の裏付けが要る。

報告の向きも反転した。採点値が回収可能額になったので、報告する価値があるのは**その上に乗っている
額面**である（`markedValueUsdc` / `summary.json` の同名フィールド）。「このポジションは
実際には受け取れない額で表示されていた、その額はこれ」という読み方になる。

### 5. 環境はエージェントの作った市場に手を出さない

フローボットとオラクル更新は環境 venue だけを触る。エージェントが作った市場は
`core/src/realtime/noArb.ts` の対象外 — 薄いエージェント製プールは fair から離れて**いてよい**。
これは構造的に保証されている: `noArb` は有効アダプタの state しか読まず、その state は
`MARKET_LEGS`（環境がデプロイした venue）から組まれる。`test/agentCreatedMarkets.test.ts` が
その境界を検査する。

帰結として明記しておく: **罠を仕掛ける者は他のエージェントからしか収穫できない。**
環境のフローからも treasury からも取れない。

### 6. 承認は被害者の問題

無制限 `approve` 経由で抜くコントラクトは規約の範囲内。参照ランタイムは環境外のコントラクトとの
やり取りごとに**必要額ちょうど**を承認し（`exactApproveTx`）、observation には registry
エントリへの未消化 allowance が出る。未知コントラクトへ `MaxUint256` を承認したエージェントは
判断をしたのである。

### 7. ガス予算（T0）

規約 §5 が上限を定めているのは 1 ブロックあたりの**本数**であって**ガス量**ではない。
エージェントが自分のコントラクトをデプロイできるようになった瞬間、その差が効く:
高価に書かれたコードへの 1 回の呼び出しがブロックガスリミットを食い尽くし、他の参加者と
**環境自身のオラクル更新**を飢えさせられる。これは対戦相手への攻撃ではなく競技基盤への攻撃なので、
規約 §6 / §8 の失格対象に書く。

1 つの数字を 3 か所が読む形にした（3 つ別々に持つと必ずズレ、ズレたときに効くのは
失格させる側である）:

| どこ | 何をするか |
|---|---|
| RPC ゲートウェイ | 署名済み tx の gas limit を RLP で読み、超過を **403 で入口拒否**（`infra/rpc-gateway/txGas.mjs`） |
| エージェントランタイム | 見積もりが超えたら送らない。1 ブロック内の累計も自己制限（`send.ts`） |
| run 後検査 | blocks.csv の `gasUsed`（receipt 由来）から per-tx / per-agent-per-block を検出（`postRunCheck.ts`） |

### 8. owner ガードは「主張」ではなく「計測」する

T0 は環境コントラクトの owner ガードを**列挙して計測せよ**と言っている。実測した
（`core/src/realtime/ownerGuards.ts`）。役割を持たないアドレスから各特権書き込みを
`eth_call` で模擬し、**revert しなかったものが穴**である。

これで実際に 2 件見つかり、塞いだ:

- `contracts/MockAggregator.sol` の `setAnswer` が誰でも呼べた。Aave のオラクルソースなので、
  全借り手の清算を決めるスイッチが開いていたことになる
- `contracts/MockOracleProvider.sol` の `setPrice` も同じ。GMX の建玉はここでマークされる

どちらも「エージェントが任意 tx を送れなかった間は結果を持たない事実」だった。それが変わる
のがこの ADR である。`agentMarkets.enabled` が true の run では、未保護の特権書き込みが
1 つでも残っていれば**起動時に落とす**。false の run では報告のみで続行する
（同じ穴に到達経路がないため、既存レジームは 1 つも壊れない）。

ソースを読むのではなく実測にしたのは、**vendor 側のコントラクトはソースが本 repo に無い**からで、
実測ならそこも同じ 1 本で覆える。

## 実測（2026-09-05）

`config/regimes/agent-markets.yaml` / seed 101 / 360 ブロック / ローカルデプロイ。
6 体（noop + 参照 4 体 + naive/verifier の対）。

| agent | netPnlUsdc | tx | 何が起きたか |
|---|---|---|---|
| `noop` | 0.0 | 0 | baseline |
| `market-launcher` | −0.2 | 5 | immutable オラクルで市場を作り、seed し、鐘の前に withdraw。損はガスだけ |
| `market-taker` | −0.1 | 6 | 正直な市場に担保を入れて借り、返して引き出した。損はガスだけ |
| `trap-launcher` | **+2,249.6** | 8 | 自分が握るオラクル・90% LLTV・無価値な自前トークン担保で、供給された USDC を borrow |
| `discovery-arb` | **−2,250.1** | 4 | registry にあるものへそのまま貸した |
| `discovery-arb-verify` | −0.1 | 3 | `oracleOwner` を読んで罠を拒否し、正直な市場だけ使って退出した |
| **合計** | **−0.9** | | ＝ ガスぶん。**捏造された価値はゼロ** |

読み取れること:

- **罠は移転として記録される。**+2,249.6 と −2,250.1 が対になり、場の合計はガス相当しか動かない。
  par でマークしていたら被害者は 10,000 のまま・攻撃者は +2,250 で、場の総和が増えていた
  （＝公理 3 が無いとどうなるか）
- **識別子が効いている。**naive と verifier の差は `oracleOwner` を読んだかどうかだけで、
  結果は −2,250 対 −0.1。ADR 0014 の「検証したかどうかだけで discrimination が決まる」形の再現
- **正直な作成者は儲からない。**−0.2 は「作って seed して抜けた」のコスト。
  誰も貸しに来なければ作成者は損をするだけで、それは正しい（作ること自体は報酬ではない）
- `scoring_unpriced_holdings` に 3 件。うち 2 件が `lending-unbacked`（罠の市場で
  裏付けを失った供給ぶん）、1 件が `lending-collateral`（環境が値付けない罠トークン担保）。
  **どれも黙って 0 にはなっていない**

owner ガード監査は **6→13 プローブすべて guarded**（`MockAggregator` / `MockOracleProvider` に
ガードを足す前は 2 件が unprotected だった）。ガス予算違反は 0 件。

| `epochMs` | 29 | 34 | 77 |

登録 20 件、`market_registration_deferred` が 2 ブロック（＝毎ブロック上限 8 が効いて繰り越した。
設計どおりで、**黙って落ちずにログに出ている**）。ガス予算違反 0・規則違反 0。
12 体 → 32 体で registryMs の p50 は 11 → 14ms、`totalMs` p50 は 58 → 64ms。
**エージェント数に対してほぼ平坦**なのは、発見コストがエージェント数ではなく
「そのブロックに現れたコントラクト数」で決まるからである。

**エージェント側**: メモリ peak 126〜133 MiB / CPU peak 51〜54%（1 コア比）。
frozen の venue-arb の既知値 ~168 MiB より軽い（このロスターは LLM を回さず、
判断も swap 主体より単純なため）。

読み取れること: **発見スイープ + registry 書き込みはブロック予算の 0.6%（p50）**、
最悪でも 2.3%。ブロックループの支配項は依然 oracle 書き込みで、本 issue はそれを動かしていない。

**受け入れていない残件**（負荷試験中に発見。本 issue の範囲外・既存）:
run が完走して `realtime simulation completed` を出したあと、**プロセスが終了しない**。
`bench/run.sh --agents 4`（本 issue と無関係な既定ロスター）でも再現するので既存の欠陥である。
run 時間制限のタイマーは `finish()` で clear されているので、event loop に別のハンドルが
残っている。**CI の `grep -q "simulation completed"` はそこまで到達しない**し、練習 devnet の
セグメント切り替えにも効くので、別 issue に分けて追う。

### 実測が見つけた欠陥（実装後・レビュー前）

live run を回さなければ出なかったものが 3 件あった。記録として残す:

1. **`repay` が正確な返済で panic した。** 債務を読む → 1 ブロック accrual が入る → 読んだ値を
   切り上げて送る → share 換算がポジションを超えて underflow。`lendingRepay max` が 16 回連続で
   revert し、借り手はエポック内に解消できなかった。`repayAll` を足し、`repay` は
   「返す share の価値を超えて引かない」ようにした
2. **`netPnlUsdc` が貸出ポジションを 0 と読んだ。** 終了時 PnL の経路は全アダプタに `null` state を
   渡すのに、こちらはそれを空 state と解釈していた。7,500 USDC を供給した貸し手が −7,500 と表示された
   （採点系列は正しかった）
3. **正直なオラクルが「自分は動かせない」と言えなかった。**`PriceFeedOracle` に `owner()` が
   無かったため、検証側が「答えない＝動かせるかもしれない」と正しく判断し、**正直な市場まで拒否した**。
   `owner()` が zero address を返すようにした

## Consequences

### 受け入れたリスク（記録するが緩和しない）

- **#55。** 罠の成功 1 件は 1 件の大きな移転であり、評価グループの標準偏差を膨らませて
  他の ~30 参加者の偏差スコアを 50 へ圧縮する。#55 は open で、これはそれを起きやすくする。
- **一度も発火しないかもしれない。** エポックは 12 分で、ADR 0020 の `scenario` リセット単位では
  **毎エポック世界を作り直す**ので、エージェントが作った市場は持ち越されない。
  「作る → 発見される → 相手を集める → 収穫する → ラウンドトリップで抜ける」を毎回 12 分で
  完了させる必要がある。しかも registry は 1 ブロック遅れ、§5 は 1 ブロック 3 本。
  この capability は一度も使われないまま終わりうる。受け入れる。
- **装飾的な金利。** 上と同じ理由で利回りの餌は効かない。LST venue の経済クロック
  （`lst.simulatedSecondsPerBlock`）を使えば直るが、同じ世界の 2 つの貸出 venue に
  別々の時計を置くことになるので却下した。
- **内部 CREATE の取りこぼし。** コントラクト内部からデプロイされたコントラクトは registry に
  見えない — そして同じ理由で誰も釣れない。

### 決めていないこと

- **「最終ブロック」を 1 点で取ること。** ラウンドトリップ規則自体は確定だが、1 瞬でマークすると
  最後の数ブロックに退出が殺到する。それを受け入れるのか、終端マークを短い窓で定義するのかは open。
- **ERC-20 判定。** ERC-165 は ERC-20 を覆わないので `name()` / `symbol()` / `decimals()` の
  static call で推測している。ヒューリスティックであることは entry の kind が
  「発見のヒントであって安全性の主張ではない」ことで受け止めている。
- **公式レジームにするかどうか。** `config/regimes/agent-markets.yaml` は
  `lst.yaml` / `liquity.yaml` と同じ**venue 単体検証用**の位置にある。公式セットは 7 本のまま。
