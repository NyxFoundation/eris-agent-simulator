# ADR 0020: 競技の world リセット単位を選択軸にする

## Status

Accepted（2026-08-19）

**実装済み（同日）**: `run.resetUnit` 軸（`sdk/src/config.ts` / `sdk/src/runConfig.ts` の `SCHEMA`）、
matrix runner だけが `scenario` を宣言できる起動時 fail-fast（`core/src/realtime/coordinator.ts`）、
`summary.json` / `matrix.json` への `resetUnit` 記録、`npm run metrics` のモード混在拒否、
**シナリオ横断集約の候補 3 本**（`core/src/scoring/aggregate.ts` = `zscore` / `borda` / `mean`、
いずれもレジーム等重み）と `npm run metrics -- --matrix <dir>` による「指標 × 集約」の総当たり比較
（§5 が要求した置き換え先の比較土台）。**まだ決めていない**のは指標と集約の**選択**そのもので、
λ が S に依存し S が #36 待ちであるため（下の「決めていないこと」）。

**測定済み（2026-08-19）**: `scenario` モードでの初測定 = `docs/scoring-metric-measurements.md` §5.8。
7 レジーム（`config/regimes/metric-*.yaml` = 公式レジームの市場条件 + ADR 0019 §6 の funding）× seed
3 本のうち **18 シナリオ成立**、1 シナリオ 29 epoch、ロスター `config/rosters/metric-field.yaml`（11 体）。
結果は **§4 の再比較を閉じられない**: 5 指標 × 3 集約の 15 通りが上位 4 体・下位 3 体で一致し、
食い違いは「noop と区別がつかない」集団の中だけだった（決め手になる中位層が空。USDC-only では
`lp-provider` が一度も取引しないため）。**再測定（2026-08-23、§5.9）で状況が変わった** — 在庫を
配らず買わせるようにしたところ 21/21 シナリオが成立し、**指標が初めて食い違った**（M4 は
`lp-provider` を 3 位、M9(λ=0.25) は 8 位 = noop より下に置く）。**指標と λ の選択は、いまや
「小さく確実に稼ぐが在庫を抱える戦略をどう扱うか」という 1 つの判断に還元されている。**得られた確定事項は 2 つ — **λ = 0.25 はここでは稼ぎ頭を
落とさない**（連続経済では落とした = λ はモードをまたげない）、**集約の選択が順位を変えないのは
M9 だけ**（ただし差が雑音の中なので弱い証拠）。副産物として環境の欠陥を 1 つ検出（21 中 3 シナリオが
同一 setup tx のタイムアウトで喪失。§5.8 (g)）。

ADR 0019（競技の採点メトリクス）の前提「本番は連続経済 1 本」を外す。0019 は Proposed のままなので
supersede ではなく**前提の差し替え**で、0019 の Decision のうちリセット単位に依存していた部分
（メトリクスの選択）は、**M9 を暫定既定に据えたまま再比較へ回す**。

## Context

eris の評価には 2 つの構造が並存している。

- **ADR 0017（シナリオベース評価、Accepted）** — シナリオ =（regime, seed）の行列を回し、
  シナリオ間は `evm_snapshot`/`evm_revert` で仕切る。`npm run backtest -- --scenarios` が実装で、
  **シナリオごとに snapshot → run → reconstruct → revert** する（`core/src/cli/backtest.ts:13-15`）。
  採点はシナリオ内 z-score → レジーム等重み平均
- **ADR 0019（採点メトリクス、Proposed）** — 本番は**連続経済 1 本** + 非公開スケジュールのイベント注入。
  4 時間 epoch の超過対数リターン系列に `score = mean(x_e) − λ·std(x_e)`（M9）

0019 が連続経済を前提に置いたのは、**本番が実チェーンだと想定していたから**である。0019 の Context は
「ADR 0017 の実行モデル（`evm_snapshot`/`evm_revert` で使い捨て世界を仕切る）には実チェーンの対応物が
無い（#33 / #35 / #36）」と書き、選択肢の評価表でも案 A / C を「105〜140 の chain 立ち上げ + venue
deploy が必要」として落としている。**リセット単位は判断の結果ではなく、実行基盤の制約だった。**

その制約が動いた。本番の実行基盤を**運営が制御する devnet** とする方針が定まり、#35 は既に
「devnet は run ごとに genesis から再起動できる（clean-slate-per-run モデルを保持する）」を
リーディング候補の利点として挙げ、work item に「**Reset strategy**: per-run chain restart from genesis
（devnet）vs fresh-deploy-per-run on a persistent chain」を持っている。つまり
**リセットできるかどうかは、もはや基盤が一方的に決める事項ではない。**

### 解決したい課題

1. **仕様が、消えた制約に固定されている** — 0019 の「world = 1」は実チェーン前提の帰結であって、
   競技設計としての判断ではない。基盤が devnet に決まった以上、前提を明示的に置き直す必要がある
2. **リセット単位が採点指標の選択を決めてしまっている** — 0019 で M9 が選ばれた第一の根拠は
   「連続経済 1 本なので案 A（M4 Gauntlet）/ 案 C（M27 Decathlon）が構造として乗らない」だった。
   world を複数回せるなら**この根拠は失われ、M4 / M27 が候補に戻る**
3. **実装は両方できるのに、仕様が片方しか認めていない** — `backtest --scenarios` はシナリオ単位
   リセットで既に動き、`sim:realtime` は連続経済で動く。**仕様だけが連続経済一本を宣言している**
4. **z-score が 2 つの宣言に挟まれて生き残っている** — 0019 は「field-relative な z-score は退役する」と
   宣言したが、シナリオ経路の `core/src/backtest/standings.ts` は今も `scenarioZScores` を使う。
   #55（参加者 1 人が場の sd を 20.9 → 181.5 に膨らませ、他全員を 8.7 倍圧縮した）は未解決のまま
5. **「リセット」の実体が環境ごとに違うのに、仕様が 1 語で扱っている** — ローカル anvil は
   `evm_snapshot`/`evm_revert`、fork は `anvil_reset` + 再 fork、devnet は **genesis からの再起動**。
   devnet には evm_revert が無いので、同じ語で書くと実装できない仕様になる

### 検討した選択肢

| | 構造 | リセット単位 |
|---|---|---|
| **A. 連続経済のみ** | ADR 0019 のまま。1 週間 = world 1 本、非公開スケジュールでイベント注入 | 無し（run 開始時のみ） |
| **B. シナリオ行列のみ** | ADR 0017 に戻す。(regime × seed) を並べ、各シナリオを独立の world で回す | シナリオごと |
| **C. リセット単位を軸にする** | 両方を仕様上のモードとして定義し、run 設定で選ぶ | 設定可能 |

### 各選択肢の評価

| 観点 | A. 連続経済のみ | B. シナリオ行列のみ | C. 軸にする |
|------|---------------|-------------------|-----------|
| 実行基盤の要求 | 最小（world 1 本） | devnet の genesis 再起動が必須 | モードごとに要求が変わる |
| 採点指標の候補 | M9 系のみ（0019 の帰結） | M4 / M27 が復活 | **本番モードの選択が候補を決める**（式自体は 1 つに統一する = Risks） |
| 1 週間に引かれたイベントへの順位依存 | **強い**（週は 1 本、引きは 1 回） | 弱い（regime × seed で平均化） | モードで選べる |
| 状態の持ち越しで測れるスキル | **測れる**（在庫・長期ポジション・レジームをまたぐ判断） | **測れない**（毎回まっさら） | モードで選べる |
| 参加者から見た本番の再現性 | 練習ハーネスと構造が違う | 練習（ADR 0016 / 0017）と同一構造 | 揃えられる |
| 実装量 | 0（現行） | 0（`backtest --scenarios` が既にある） | **設定軸 + 採点の統一が要る** |
| #55（外れ値脆弱性） | 解消済み（自分の系列のみ） | z-score のままなら**未解決** | 採点の統一で解消させる必要がある |

A と B はどちらも「測れるもの」を片方捨てる。**連続経済でしか測れないスキル**（イベントをまたいで
在庫を持ち越す判断、drawdown からの回復、1 本のパスでの資本配分）と、**シナリオ行列でしか得られない
性質**（同じ戦略を複数のレジーム × seed で回して、順位が「その週に何が来たか」に依存しないようにする）
は排他で、どちらが競技として正しいかは環境の較正とイベント密度に依存する。

**C を採る。ただし「決めない」という意味ではない。** 軸を残すのは較正・練習・将来の回のためで、
**今回の本番は `scenario`** と決める（§2）。仕様が軸を持つことと、本番の設定値が決まっていることは
別で、0019 が固定していたのは前者だった。

## Decision

**world のリセット単位を仕様上の選択軸 `run.resetUnit` とし、`continuous`（連続経済 1 本、既定）と
`scenario`（シナリオごとに world をリセット）の 2 値を取る。本番の実行基盤は運営が制御する devnet と
し、リセットの実体は環境ごとに 3 実装を持つ。本番競技は `scenario` モードで行う**（ADR 0019 の
「本番 = 連続経済 1 本」を差し替える）。**採点指標は ADR 0019 の M9 を暫定既定として維持しつつ、
選択の第一根拠が消えたため `scenario` モードで M4 / M9 / M27 を再比較する。**

### 1. `run.resetUnit` — 2 つのモード

```yaml
run:
  resetUnit: continuous   # 既定。1 週間 = world 1 本（ADR 0019 の構造）
  # resetUnit: scenario   # (regime, seed) ごとに world をリセット（ADR 0017 の構造）
```

`sdk/src/runConfig.ts` の `SCHEMA` に `"run.resetUnit": "ERIS_RESET_UNIT"` を足す。
`scenario` は `--scenarios <path>` を伴い、それ無しで指定されたら**起動時 fail-fast**
（黙って連続経済で走ると、リセットされたつもりの順位が出る）。

| | `continuous` | `scenario` |
|---|---|---|
| world の数 | 1 | シナリオ数（regimes × seeds） |
| イベント | 非公開スケジュールで 1 本の週に注入 | regime YAML がレンジ、seed が実現値 |
| 現行の入口 | `npm run sim:realtime` | `npm run backtest -- --scenarios` |
| epoch 数 E | 週全体（本番 42 / 検証 41） | **シナリオごとに短くなる**（直列なら 42 ÷ シナリオ数 S） |
| 状態の持ち越し | あり | 無し（毎シナリオ初期配布から） |

**E が変わることは採点に直接効く。** `docs/scoring-metric-measurements.md` §5.6 の実測どおり
実効的な厳しさは `λ / √(epoch 長)` で動くので、**`continuous` で較正した λ をそのまま `scenario` に
持ち込むことはできない**。モードごとに較正が要る。

### 2. 本番競技は `scenario` モードで行う

**本番（1 週間・数百人・運営 devnet）は `scenario` を採る。** ADR 0019 の前提「本番 = 連続経済 1 本」は
ここで差し替わる。根拠は 3 つ:

- **順位を「その週に何が引かれたか」から切り離す** — 連続経済では週が 1 本、イベントの引きも 1 回で、
  非公開スケジュールが誰の戦略に仕事を作るかが順位に直接効く。単一種のイベントで埋めた週は特定の
  戦略にしか仕事を作らないことは実測済み（depeg だけの週で venue-arb が 5 seed 中 3 本で無取引 =
  `docs/scoring-metric-measurements.md`）。(regime × seed) で回せばこの依存が平均化される
- **練習と本番の構造が一致する** — ADR 0016 / 0017 の `backtest` はシナリオ単位リセット。参加者は
  本番と同じ構造で練習でき、提出前の自己検証がそのまま予行になる（`continuous` を本番にすると
  練習ハーネスと構造が違ってしまう）
- **devnet なら実行できる** — genesis 再起動という実体を持てる（#35）。ADR 0019 が案 B を落とした
  唯一の理由（実チェーンに `evm_revert` の対応物が無い）は消えている

**引き換えに捨てるもの**（不足ではなく意図的な取捨）: 在庫の持ち越し、drawdown からの回復、複数の
レジームをまたぐ資本配分。**これらは競技の対象外**とする。各シナリオは初期配布から始まり、
シナリオ内で完結するリスク管理だけが測られる。

`continuous` は仕様から落とさない。連続経済でしか出ない性質（長い E での λ の効き方、持ち越しを
含む戦略の挙動）の較正と、`sim:realtime` による日常の開発・デバッグに使う。**既定値が `continuous`
なのは現行 `sim:realtime` との互換であって本番の宣言ではない**（本番 config は `resetUnit: scenario`
を明示的に書く）。

**これでクリティカルパスが動く**: シナリオ横断の集約式（§5）と `scenario` 側の λ 較正が本番の
ブロッカーになり、devnet の genesis 再起動時間（#36）がシナリオ数 = 競技の解像度を直接決める。

**シナリオを直列に並べるか並列に走らせるかは、この ADR では決めない。** 本番は 1 週間の実時間なので、
**直列**（週を S 分割）だと 1 シナリオの epoch 数が `42 ÷ S` まで縮み、S を増やすほど引きの運は
平均化される代わりに 1 シナリオ内の std が意味を失う。**並列**（S 本の devnet を同時に走らせ、
各シナリオが週全体を使う）ならこのトレードオフは消えるが、参加者ごとに S 本の agent プロセスと
S 本の devnet が要る。どちらが乗るかは #36 の容量実測に依存する。

### 3. リセットの実体は環境ごとに 3 つ

「world をリセットする」は 1 つの操作ではない。仕様は**満たすべき事後条件**で書き、実装は環境が選ぶ。

| 環境 | 実装 | 実体 |
|---|---|---|
| ローカルデプロイ anvil | `resetFork`（`sdk/src/chain.ts:291`） | `evm_snapshot` / `evm_revert` でクリーン断面へ戻す |
| fork anvil | `resetFork` | `anvil_reset` + 上流からの再 fork |
| **運営 devnet（本番）** | **genesis からのチェーン再起動**、または fresh-deploy-per-scenario | `evm_revert` は**存在しない**（#33 item 3 / #35 work item） |

**事後条件**（3 実装が共通で満たすもの）:

- 全 venue が deploy 済みで、シード流動性が初期較正値に戻っている
- 全参加者ウォレットが初期配布ちょうどを持ち、**前シナリオのポジションが 1 つも残っていない**
  （Aave の残債・Trove・LP NFT・GMX 建玉を含む。soft reset での残留は既知の壊れ方 =
  ADR 0009 §4 / ADR 0016 §2 が victim 建立に fresh state を要求しているのと同じ理由）
- 採点の再構成が**リセットより前に完了している**（`reconstruct.ts` は歴史ブロックを読むので、
  revert / 再起動が歴史を消すと読めなくなる。`backtest` が既にこの順序を守っている）

devnet の genesis 再起動は anvil の revert より**桁違いに遅い**ので、シナリオ数 × 再起動時間が
run 全体の下限になる。`scenario` モードのシナリオ数はこの予算から決める（#36 の RPC 実測待ち）。

### 4. 採点指標 — M9 を暫定既定として維持し、`scenario` で再比較する

ADR 0019 の Decision（M9 = `mean − λ·std`）は**撤回しない。暫定既定として維持する。**
第一根拠は消えたが、**式が悪いと分かったわけではない**し、宣言された採点式が 1 つも無い期間を作ると
`core/src/backtest/standings.ts` の z-score が既定のまま残り続ける（#55 が未解決のまま固定される）。
実装（z-score の退役・本番採点パス）は M9 を前提に進めてよい。

0019 の論理は次の 2 段だった:

1. 本番は world 1 本 → 案 A（M4）/ 案 C（M27）は ~105 世界を要求するので構造的に乗らない
2. 残った M4 と M9 の差は `λ·std` 項だけ（`x_e` が対数リターンなので mean 項は telescope する）
   → リスクを罰する項を持つ側を採る

**2 は今も有効で、1 が失われた。** 本番が `scenario` になったことで案 A / 案 C は構造的に成立するので、
M4 / M9 / M27 の比較をやり直す。ただし**成立の度合いはシナリオ数 S に依る**（§2 の直列/並列が未決なので
S も未決）。順位化に基づく M27 は S が小さいほど解像度を失うため、比較は S の候補値ごとに見る。

再検討は**再 run 不要**で始められる。`npm run metrics -- <runDir...>` が保存済みの epoch 系列から
M1 / M4 / M7 / M9 / M13 と M27 Borda を既に全部計算する（issue #56）。`matrix.json` はシナリオ ×
agent の生スコアを持つので、シナリオ横断の集約も再計算できる（ADR 0017 §4 が約束した性質）。
測定の記録は `docs/scoring-metric-measurements.md` に追記する。

**この ADR は指標を確定しない。** 置くのは**暫定既定（M9）と再比較の義務**、および
「リセット単位が指標選択の入力である」という関係だけで、確定は #56 に戻す。

### 5. z-score は退役させる — 置き換え先は本番のブロッカー

ADR 0019 の「field-relative な z-score は退役する」は**リセット単位と独立に有効**である。#55 は
「参加者 1 人が場の sd を膨らませて他全員を圧縮する」という field-relative 正規化そのものの性質で、
world をリセットしても消えない。

そして**本番が `scenario` になったことで、シナリオ横断の集約は本番のクリティカルパス上に乗った**
（`continuous` にはそもそも集約が無いので、0019 の下では「集約式を決める」という作業自体が無かった）。
現行 `core/src/backtest/standings.ts` の `scenarioZScores` がその役目を担っているので、
**退役には置き換え先の決定が前提**になる。§4 の再検討と同じ作業単位に入れる。

候補は M27 Borda（順位化なので外れ値に構造的に強い。`bordaTotals` として実装済み）か、
シナリオ内でベンチマーク相対の絶対量を取ってから平均する形。**どちらも #56 で決める。**

### 6. 何を測るモードなのかを rules text に書き分ける

2 モードは同じ競技の設定違いではなく、**測っている能力が違う**。参加者向けの文言は本番モード
（`scenario`）のものを書き、`continuous` は較正・練習用のモードとして区別できるようにしておく。

- **`scenario`（本番）** — 同じ戦略を複数の (regime, seed) で回す。**引きの運を平均化**できる代わりに、
  状態の持ち越しで測れるものが消える。**各シナリオは初期配布から始まり、前のシナリオの在庫・
  ポジション・学習結果はいずれも引き継がれない**（agent プロセス内の記憶を含め、シナリオ間で
  持ち越せる前提を置いた戦略は成立しないことを明記する）
- `continuous`（較正・練習用） — 1 本の経済を 1 週間走り切る。在庫の持ち越し、drawdown からの回復、
  イベントをまたぐ資本配分が測れる。順位は**その週に引かれたイベントに依存する**

## Consequences

### Positive

- **仕様が実行基盤の制約から独立する。** 0019 の「world = 1」は devnet が決まった時点で根拠を失って
  いた。軸にすることで、基盤が変わっても仕様を書き直さずに済む
- **練習ハーネスと本番の構造が一致する。** ADR 0016 / 0017 の `backtest` はシナリオ単位リセットで、
  本番も `scenario` なので、参加者は本番と同じ構造で練習できる（0019 の下では練習と本番の構造が違った）
- **順位が「その週の引き」に依存しなくなる。** (regime × seed) で平均化されるので、非公開スケジュールの
  1 回の引きが誰の戦略に仕事を作ったかで順位が決まる度合いが下がる
- **採点指標の比較が再 run なしで始められる。** #56 の `metrics` ツールと `matrix.json` が既にある
- **実装量が小さい。** リセット機構は 3 実装のうち 2 つが動いており、devnet 側は #35 の work item に
  既に入っている。本番経路は `backtest --scenarios` と同じ構造なので、新規は設定軸と採点の統一

### Negative

- **本番に要る λ は未較正の側である。** 手元にある値（0019 の宣言 λ = 0.25、測定記録の推奨 0.15）は
  どちらも**連続経済 × 12 ブロック epoch** で出たもので、そのままは持ち込めない
  （実効的な厳しさは `λ/√(epoch 長)` で動く = 測定記録 §5.6）。しかも `scenario` の epoch 数は
  シナリオ数 S に依存する（直列なら `42 ÷ S`）ので、**S が決まるまで本番の λ は較正できない**
  - → 較正の優先順位が入れ替わる。保存済み run から再採点できるので追加 run は最小で済むが、
    S 候補ごとに見る必要がある
- **採点指標の再比較が本番前に要る。** #56 は「測定は完了、残るは λ と epoch 長の判断」まで来ていたのが、
  候補の再比較まで戻る（既定は M9 のままなので実装は止まらない）
  - → 2 段は生きている（M4 と M9 の差は `λ·std` 項だけ）ので、比較は M4 / M9 / M27 の 3 つに絞れる
- **持ち越しで測れるスキルを競技から外す。** 在庫の繰越・drawdown からの回復・レジームをまたぐ
  資本配分は本番では評価されない。「1 週間の DeFi トレード競争」という言葉から参加者が期待する
  ものとずれる可能性がある
  - → §6 の rules text で明示する。`continuous` はモードとして残るので、将来の回で採ることはできる
- **モードが 2 つあると、どちらの数字か分からない結果が生まれる。** 過去 run との比較が壊れる
  （#27 で公式レジームが 7 本になったとき matrix が比較不能になったのと同じ壊れ方）
  - → `summary.json` / `matrix.json` に `resetUnit` を必ず書き出し、モードをまたぐ集計は fail-fast
- **devnet の genesis 再起動時間が競技の解像度を決める。** 本番が `scenario` なので、
  再起動 × シナリオ数が実時間の予算に直接効き、S を増やせないと引きの運の平均化も効かない
  - → S は #36 の実測後に決める。それまでは poc の anvil で較正する

### Risks

- **devnet の「リセット」が事後条件を満たさない可能性。** genesis 再起動は本来クリーンだが、
  再デプロイのたびにアドレスが変わると参加者の定数が壊れる
  - → deployments を manifest 化して配布する仕組みは ADR 0016（state dump + fingerprint）に既にある。
    devnet でも同じ規律を適用し、fingerprint 不一致は fail-fast
- **「毎回まっさら」が戦略を単純化しすぎる可能性（本番のリスクになった）。** 持ち越しが無いと
  リスク管理の大半（ポジションの繰越、段階的な積み上げ）が測れず、さらに 1 シナリオが短いほど
  「開幕に全力で張る」が最適に寄る
  - → 1 シナリオの長さは、**シナリオ内でリスク管理が意味を持つ最小の epoch 数**を下限として決める。
    これは S を増やす方向（引きの平均化）と正面から競合するので、S の決定はこの 2 つの綱引きになる
- **シナリオ間で状態を持ち越さないことの強制が未実装。** 現行 `backtest --scenarios` は
  シナリオごとに coordinator を回すので agent プロセスは再起動されるが、**ファイルシステムに
  書けば持ち越せる**。本番では「前のシナリオで得た情報を次で使う」が抜け道になる
  - → 本番実行時に作業ディレクトリを初期化するか、持ち越しを明示的に許すかを決める（未決）。
    ルール文だけで塞がるものではない
- **2 モードを維持する保守コスト。** 採点・レポート・rules text が二重化する
  - → 採点の**式**は共通にし（§4 の再検討で 1 つに決める）、違いは epoch 系列の作り方と集約の有無だけに
    閉じ込める。モードごとに別の式を持たせない

## 決めていないこと

| 項目 | 決めない理由 | いつ決めるか |
|------|------------|------------|
| シナリオを直列に並べるか並列に走らせるか | 直列は 1 シナリオを `42 ÷ S` epoch に縮め、並列は参加者ごとに S 本の devnet と agent プロセスを要求する。どちらが乗るかは容量次第 | #36 の後 |
| 採点指標の確定（M4 / M9 / M27） | 第一根拠が消えたので再比較が要る。保存データから始められる。**確定までの既定は M9**（§4） | #56 |
| シナリオ横断の集約式（z-score の置き換え先） | 指標の選択と同じ作業単位。**本番が `scenario` なのでブロッカー** | #56 |
| λ と epoch 長（モードごと） | E がモードとシナリオ数 S で変わるため、指標と S が決まるまで較正できない | 指標決定 + S 決定後 |
| devnet のリセット実装（genesis 再起動 vs fresh-deploy） | #35 の work item であり、ops 側の選択 | #35 |
| シナリオ数 S と、その内訳（regime × seed の取り方） | devnet の再起動時間の実測と、1 シナリオの最小長（Risks）の綱引きで決まる | #36 の後 |
| シナリオ間の持ち越し禁止をどう強制するか | プロセス再起動だけでは塞がらない（ファイルシステム）。ops の実行形態に依存する | 本番実行形態の確定時 |
| 練習ハーネス（ADR 0016 / 0017）の採点を本番に揃えるか | 練習の目的は執行の練習であって順位の予習ではない（0019 §決めていないこと から引き継ぎ） | 本番の採点が動いた後 |

## Notes

### ADR 0019 との関係

0019 は Proposed のままなので supersede しない。**差し替えるのは前提（Context の「本番は連続経済
1 本」）と、そこから出ていた「案 A / 案 C は構造として乗らない」という排除だけ。** Decision の M9 は
暫定既定として生き、`scenario` モードでの再比較にかかる（§4）。0019 の以下も生きている:

- §1 の telescope の性質（M4 と M9 の差は `λ·std` 項だけ）と、そこから出る G4 不要 / G7 全境界
- §2 のベンチマーク = noop（差し引きは実エントリで、mean 項では共通定数、std 項にだけ効く）
- §3 の `x_e` は通常の live mark（`alphaValueUsdc` ではない）
- §5 のゲート G1–G7、§6 の funding、§8 の epoch 境界と欠測
